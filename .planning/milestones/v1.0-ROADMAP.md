## Overview

GameKit v1.0 delivers a GPL, self-hostable, composable .NET 10 game-services backend as **7 independent NuGet packages** (Core, Auth, Rankings, Matchmaking, Presence, Admin.UI, OpenApi) plus a CLI, a build-time source generator, and a `dotnet new gamekit` template. Every algorithm — matchmaking strategy, ranking algorithm, password hasher, OAuth provider — is a DI-swappable interface, and the entire stack runs on nothing but Postgres + Redis + the consumer's ASP.NET Core host. No cloud, no telemetry, no phone-home.

## Key Accomplishments

1. **Coordinated 7-package release train** — all packages stamp one MinVer-derived `GameKitVersion`, sibling references are pack-time exact-pinned `[X.Y.Z]` (D-26 nuspec guard), and a startup `GameKitVersionAssertionHostedService` (registered at DI index 0) fails fast on any cross-assembly version mismatch.
2. **Full authentication stack** — Steam (in-house OpenID 2.0 with server-side `check_authentication`), Discord (`identify`-only), Guest, and Username/Password (BCrypt) providers; rotating JWTs with reuse-attack family revocation + a 45s mobile-resume grace window; SERIALIZABLE guest→account upgrade protected by a unique constraint.
3. **Rankings + sessions + GDPR** — vendored Glicko-2 (BSD-3-Clause, attributed), batched windowed `IRankingAlgorithm.Apply`, idempotent `POST /api/sessions/{id}/complete` (state-conditional + `Idempotency-Key`), seasonal archive/reset, full GDPR export, and audited manual rank-adjust.
4. **Crash-safe matchmaking** — Redis-lease live queue with an atomic Lua claim (no double-match), party-aware EloRange strategy with time-based bracket flex (±100→±500), Redis leader election, and a reconciler that never rehydrates Redis from Postgres. Phase-gated by a 100-party chaos test and a 1k-ticket/10-minute load test (final run: MaxIterationMs=29, Dropped=0, Matched=3092).
5. **Blazor Server Admin UI** (violet hi-fi redesign) — default-deny mount (404 in Prod), separate cookie auth scheme isolated from player JWTs, player search/ban/audit, ⌘K command palette, and health + queue-depth + presence panels that gracefully degrade when their backing package is absent; CSP nonce + anti-CSRF on every mutation.
6. **Presence + production ops** — Redis-only presence with game-server-authoritative state machine (online/offline/in-match), full OpenAPI coverage (contract-tested against `EndpointDataSource`), a 9-file deployment guide (bare-metal/container/air-gapped + 3-role Postgres, Redis AOF, JWT keys, disaster recovery, migrations runbook), and a 2-process `gamekit_reader` reference topology.

## Carried-Forward Tech Debt (v1.x backlog)

Per the milestone audit — none block v1.0; all are documented for the next milestone:

- **Matchmaking is rating-blind in v1** — `EloRangeMatchmakingStrategy` operates on rating=0 because Matchmaking deliberately takes no Rankings runtime dependency. Match formation works; skill-based ordering does not. Wiring Rankings → Matchmaking ratings is the headline v1.x item.
- **Admin "Rank adjust" nav page is a dead stub** — the functional rank-adjust path (dialog + `POST /admin/api/players/{id}/rank-adjust`) is fully wired; only the sidebar nav entry point renders a placeholder.
- **3 phases lack a VERIFICATION.md artifact** (01, 03, 05) — ground-truthed complete during the audit; backfill optional.
- **OPS-07 doc drift** — egress guard is satisfied by reflection-based `EgressGuardTests`; ROADMAP's claim of a CI `unshare --net` layer is overstated.
- **Deferred test-coverage naming gaps** (Phase 4 SC#5/SC#6) and WR-11 test-side SQL interpolation — flagged in 04-VERIFICATION.md.

## Phase Success Criteria (as verified)

### Phase 1 — Foundation
Goal: Prove the multi-package migration pattern on `GameKit.Core` and establish license, ops, and anti-egress defaults.
SCs: (1) `AddGameKit().UseGameKit()` creates `gamekit` schema + core tables + `__ef_migrations_core`; (2) CI clean-install migration test, no snapshot drift; (3) GDPR delete tombstone + opponent FK null; (4) zero-egress runtime guard test; (5) three-role Postgres + Redis AOF role-isolation test; (6) GPL header CI check. **7/7 plans complete.**

### Phase 2 — Authentication
Goal: Players authenticate via Steam/Discord/guest/password, receive rotating JWTs with reuse-attack protection that tolerates mobile resume, and upgrade guests without race corruption.
SCs: (1) E2E login all 4 providers + refresh rotation; (2) forged Steam callback rejected; (3) concurrent-refresh grace vs family-revoke; (4) concurrent guest-upgrade unique-constraint; (5) link-or-switch challenge; (6) rate-limit 429s. **8/8 plans complete.**

### Phase 3 / 3.1 — Admin UI
Goal: Mount a Blazor Server admin console at a chosen path, separate auth scheme, audited player management, never exposed to unauthenticated traffic.
SCs: (1) mount + bootstrap admin + search; (2) 404 in Prod + fail-fast no-role; (3) audited ban/unban; (4) match-history/health/rank-adjust/queue-depth panels with package placeholders; (5) CSRF + CSP; (6) player JWT cannot reach admin. Redesign 3.1: violet visual match, Tweaks persistence, no functional regression, component tests, ≤25KB CSS, WCAG AA. **13/13 + 11/11 plans complete.**

### Phase 4 — Rankings + Sessions + GDPR
Goal: Idempotent windowed Glicko-2 rating updates a developer can swap, lossless seasonal boundaries, GDPR export over full PII surface.
SCs: (1) 1000-match convergence within Glickman tolerance, batched-only; (2) idempotent session-complete (5× = 1 delta); (3) double-precision rating columns + participant snapshots; (4) seasonal archive + archived leaderboard queries; (5) GDPR export bundle contract; (6) atomic audited rank-adjust. **8/8 plans complete.**

### Phase 5 — Matchmaking + Parties
Goal: Solo/party 1-N players queue into a Redis matchmaker that never double-matches, survives crashes, flexes brackets, holds 1k-ticket load.
SCs: (1) party ticket + bracket flex + async Postgres analytics; (2) chaos test (kill mid-match → no dup sessions/ghost tickets); (3) 1k/10-min load gate; (4) leader-election failover; (5) per-player enqueue rate limit; (6) Admin queue-depth/health from live Redis. **10/10 plans complete.**

### Phase 6 — Presence + OpenAPI + Distribution
Goal: Presence lights up Admin UI + gates abandonment, every endpoint described by OpenAPI, newcomer goes `dotnet new gamekit` → running backend on the coordinated release train.
SCs: (1) game-server-authoritative presence state machine; (2) Admin presence panel + graceful degrade; (3) OpenAPI covers every endpoint (contract test); (4) template + 2-process reader topology + reader-INSERT-denied test; (5) release-train version stamp + exact-pin + mismatch assertion; (6) 9-file ops guide + CS1591-as-error across all packages. **10/10 plans complete (20/20 must-haves verified).**
