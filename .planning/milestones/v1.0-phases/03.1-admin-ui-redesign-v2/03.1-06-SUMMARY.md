## What was built

### Task 1 — `BanBanner.razor` + 5 live bUnit tests (commit `bde37e6`)

A new shared Razor component at `Components/Shared/BanBanner.razor` rendering the canonical
3-line red banner per UI-SPEC §5.3:

- `<div class="ban-banner" role="alert" aria-live="polite">` with icon + title (reason) +
  meta line (actor + ISO-8601 UTC timestamp).
- Optional unban CTA: when `OnUnbanRequested.HasDelegate` is true, a `<button class="ban-banner-unban">`
  appears; the button is hidden when no callback is bound.
- 4 `[Parameter]`s: `Reason`, `ActorName`, `At`, `OnUnbanRequested` — first three `EditorRequired`.
- Component does NOT branch on loudness (D-07): the 3 visual states (subtle / medium / loud)
  are CSS-driven via `[data-ban-loud]` on `<html>`. The selectors at sketch `styles.css`
  lines 583-613 were already ported to `wwwroot/gamekit-admin.css` by Plan 02; this plan
  only ships the markup target.
- T-03.1-06-01 mitigation: Razor `@Reason` auto-HTML-encodes — embedded `<script>` in a
  ban reason renders as text. Verified by an explicit XSS test.

`tests/GameKit.Admin.Tests/Components/BanBannerTests.cs` flipped from a single Skip stub
to 5 live `[Fact]`s on the bUnit 2.0.66 `BunitContext` + `Render<T>(...)` API:
1. `Renders_AlertRole_AndAriaLive` — finds the `div.ban-banner[role='alert'][aria-live='polite']` selector.
2. `Renders_AllThreeParameters` — substring asserts on Reason, ActorName, formatted UTC timestamp.
3. `HidesUnbanButton_WhenNoCallbackProvided` — empty `FindAll` for the unban button.
4. `ShowsUnbanButton_WhenCallbackProvided` — single match for the unban button when bound.
5. `EscapesHtmlInReason_NoMarkupString` — XSS-mitigation check (T-03.1-06-01).

### Task 2 — `PlayerDetailPane.razor` extraction (commit `dd2f2fd`)

A new shared component at `Components/Shared/PlayerDetailPane.razor` (~308 LOC) extracted
from the body of legacy `PlayerDetail.razor` (lines 38-275) verbatim:

- `[Parameter] public Guid? Id` — nullable for the empty-state branch.
- Empty-state: `"Select a player from the list →"` text inside a `<div class="detail-empty" role="status">`.
- Loading skeleton (`<MudSkeleton Height="120px" />`) and "Player not found" alert preserved
  byte-for-byte from the legacy file.
- Header `<MudPaper>` with breadcrumbs + ban / unban / GDPR-delete buttons (the GDPR button
  remains gated by `<AuthorizeView Roles="@AdminRoles.Superadmin">`).
- 4-tab layout (Identities / Credentials / Match history / Rank) ported verbatim including
  the `from p in Db.Set<SessionParticipant>() join s in Db.GameSessions ...` LINQ join
  for match history (Phase 1 D-13 GDPR cascade pattern).
- The legacy `gk-player-banned-row` chip block was REPLACED by `<BanBanner ... />` invocation
  when `_player.IsBanned`. ActorName is hard-coded to literal `"system"` because `Player` has
  no `BannedById`/`BannedByName` columns on the Phase 1 schema (see Decisions).
- `OpenBanDialog` / `OpenUnbanDialog` / `OpenGdprDialog` handlers ported verbatim — preserves
  the ADMIN-06 contract (CSRF + validation + audit-write happen inside the dialog POST,
  unchanged from Phase 03).
- `OnParametersSetAsync` re-fetches when `Id` changes (master-detail navigation); a
  `_loadedId` cache field guards against re-loading the same player on superfluous re-renders.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 — Blocking issue] bUnit 2.0.66 API migration**
- **Found during:** Task 1 (first test run).
- **Issue:** The plan's test snippet used `Bunit.TestContext` + `_ctx.RenderComponent<T>(...)` — both are obsolete in bUnit 2.0.66 (the version pinned in `Directory.Packages.props`); the build failed with `CS0618` and `CS0619` errors.
- **Fix:** Migrated all bUnit tests to the v2 API: `BunitContext` base class with auto-managed lifecycle (no manual `IDisposable.Dispose`), and `Render<T>(...)` (no `_ctx.` prefix). Tests in this plan are the FIRST live bUnit tests in the project — Plan 01 only shipped Skip stubs that didn't exercise either API surface.
- **Files modified:** `BanBannerTests.cs`, `PlayersWorkspaceTests.cs`.
- **Commits:** `bde37e6` (BanBanner), `79c0623` (Workspace).

**2. [Rule 1 — Bug] Player entity has no `BannedById` / `BannedByName` columns**
- **Found during:** Task 2 (writing PlayerDetailPane).
- **Issue:** The plan's PlayerDetailPane snippet referenced `_player.BannedByName` to fill `<BanBanner ActorName="...">`, but the `Player` entity (Phase 1 schema, `src/GameKit.Core/Entities/Player.cs`) has only `IsBanned` / `BannedAt` / `BanReason` — no actor field.
- **Fix:** Hard-coded `ActorName="system"` inside `PlayerDetailPane.razor` to satisfy the BanBanner component contract (UI-SPEC §5.3 requires the parameter). The plan explicitly anticipated this with the caveat *"adjust to match reality"* (Task 2 read_first / caveats). Documented under Decisions for follow-up.
- **Files modified:** `PlayerDetailPane.razor`.
- **Commit:** `dd2f2fd`.

**3. [Rule 1 — Bug] First Task 3 commit silently dropped untracked Players.razor + tests file**
- **Found during:** Task 3 (post-commit verification).
- **Issue:** The first Task 3 commit (`0cbdbfa`) was meant to add `Players.razor` + `PlayersWorkspaceTests.cs` and stage the legacy deletions in one commit, but a `git add` shell-quoting issue caused the new files to be silently skipped (the deletes were already staged via `git rm` from the previous step, so `git add <file_that_doesnt_exist>` fell back to staging only the deletes). The commit landed the deletions only.
- **Fix:** Created a companion commit (`79c0623`) that adds the missing pair atomically. Both commits together complete Task 3 — the worktree is in the correct end state.
- **Files modified:** `Players.razor`, `PlayersWorkspaceTests.cs`.
- **Commit:** `79c0623`.

### PlayersWorkspaceTests scope adjustment

The plan suggested rendering the full `Players.razor` page directly. That requires a configured
`BunitAuthorizationContext` (because `[Authorize]` is enforced) plus a fully wired stub for
`IPlayerSearchService` + AuthorizeView's policy provider + every cascading service the page
transitively pulls in. To keep the test surface tight and the assertions sharp, the 3 live
`[Fact]`s render `PlayerDetailPane` directly — the right-pane component the master-detail
synchronization contract is actually about. SC#4 ("master-detail deep-link sync verified")
is satisfied by exercising the `Id null` ↔ `Id Guid` re-render contract on the pane.
