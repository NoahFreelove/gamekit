<objective>
The matchmaker ticker — the live engine that turns Redis-queued tickets into proposals. This is the single most complex service in Phase 5 because it interlocks five primitives: the lease helper, the strategy, the Lua claim script, the proposal sweeper, and the OTel instrumentation. Phase 4 set the template; this plan applies it to matchmaking.

Purpose: Land MATCH-07 (BackgroundService + PeriodicTimer + Polly v8) and MATCH-08 (leader-election via Redis lock) with the correctness behaviors that SC#4 (leader-election test) and Pitfall §10 (proposal-sweep) require. Without this plan, no live matching happens — proposals never form, the strategy is never invoked at runtime.

Output: Lease helper, ticker BackgroundService, proposal sweeper, OTel ActivitySource, builder wiring, plus the SC#4 phase-gate leader-election integration test + a separate ProposalSweep integration test for Pitfall §10.

**Channel<TicketEvent> dependency note (Wave 3 ordering fix):** The ticker resolves `ChannelWriter<TicketEvent>` from DI to enqueue per-tick TicketEvent rows. The Channel singleton + writer + reader are registered as a placeholder (capacity 1000, DropNewest) inside Plan 05-04's `MatchmakingBuilderExtensions.Strategy.cs` so this plan can run without depending on Plan 05-07 having shipped. Plan 05-07's `MatchmakingBuilderExtensions.Background.cs` later `services.Replace(...)` the placeholder with the options-driven bounded channel (capacity 10000 per D-15). The ticker integration tests therefore work standalone in Wave 3 — they receive the placeholder writer.

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05-01 | Tampering | Two replicas double-match same ticket pair during lease handoff | mitigate | AtomicClaimScript fencing check inside Lua (Pitfall §2 — Plan 05-04); RenewLeaseAsync before each pool with bail-on-false (Plan 05-05); MatchmakingLeaderElectionTests SC#4 verifies under concurrency |
| T-05-05-02 | Denial of Service | Ticker loop exceeds tick budget under load (1k tickets) — lock expires mid-tick | mitigate | LockTtlSeconds (90s default) >> typical tick budget (50ms target per RESEARCH §Decision 13); RenewLeaseAsync between pools; SC#3 load test (Plan 05-10) verifies budget at 1k tickets |
| T-05-05-03 | Information Disclosure | Long-running ticker leaks lease (replica crashes between RunOnceAsync and ReleaseLeaseAsync) | accept | LockTtlSeconds expires naturally; new replica acquires after expiry (proven by Forced_Failover test); cost = up to LockTtlSeconds of no matching, acceptable for a self-hosted backend |
| T-05-05-04 | Tampering | Reaped proposal's accepting parties re-ZADDed with INCORRECT queuedAt (D-09 violation) | mitigate | ProposalSweepTests asserts original queuedAt preserved in re-ZADD; the ticker reads the ticket hash's `queuedAt` field (set at enqueue, never mutated) — not the current time |
</threat_model>
