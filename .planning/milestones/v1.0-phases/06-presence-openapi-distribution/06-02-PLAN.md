<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Cross-package assembly version trust | Consumer's restore graph could pull mismatched GameKit.* versions; runtime would silently produce divergent behavior without the version-assertion hosted service |
| Reflection scope of GameKitVersionAssertionHostedService | The service reflects on AppDomain assemblies — any other assembly happening to expose a `*.Internal.GameKitMarker.GameKitVersion` constant would be picked up, but only `GameKit.*`-named assemblies are filtered |
| ISessionLifecycleObserver implementations | Run inside the caller's ambient DB transaction; a malicious/buggy observer could roll back the session-state transition. Mitigated by D-21 contract (observer MUST be idempotent + must not throw under non-fatal conditions) — same pattern as IPostSessionCompleteHandler |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Tampering / EoP | GameKitVersionMismatchException is only thrown at IHost.StartAsync — if a consumer registers their own Insert(N>0, IHostedService) that runs before the assertion, version mismatch could leak past startup | mitigate | (a) `services.Insert(0, ...)` is the explicit registration position; (b) PATTERNS warning #2 documents the constraint; (c) D-16 + RESEARCH §"NEW: required ports" specifies "registered AUTOMATICALLY by AddGameKit() in Core" so consumers don't manually wire it. A consumer who Inserts ahead of position 0 is opting out of the safety net deliberately. |
| T-06-02-02 | Information disclosure | GameKitVersionMismatchException.Message exposes the per-assembly version map | accept | (a) Versions are NOT secrets — they are stamped publicly into every NuGet package's `info.version` and exposed by D-22 `info.version` in the OpenAPI doc; (b) the exception fires at startup and bubbles to the consumer's logging, NOT to an HTTP response — no observable info-disclosure surface to a network attacker. |
| T-06-02-03 | Tampering | Reflection on AppDomain assemblies is unsandboxed | accept | The service runs inside the consumer's process with the consumer's privileges; reflection on assemblies the consumer already loaded is a normal hosting-extension operation (mirrors the existing AuthMigrationHostedService / RankingsMigrationHostedService reflective registration patterns). |
| T-06-02-04 | DoS | A consumer with many transitively-referenced assemblies could see slow startup from the eager-load + iterate cycle | accept | (a) Eager-load is filtered to `GameKit.*` names — bounded to 7 packages; (b) AppDomain iteration is O(loaded-assembly-count) and runs once per process lifetime, not per request; cost <1ms per RESEARCH §Pattern 6 caveat line 726. |
| T-06-02-05 | Spoofing | A consumer assembly named `GameKit.Evil` would be inspected by the assertion service and its (fake) GameKitMarker.GameKitVersion would participate in the consistency check | mitigate | (a) Filter is `"GameKit."` prefix Ordinal — collision requires deliberate consumer choice; (b) the source generator emits the marker only when the assembly name starts with `"GameKit."` (Pattern 5 line 644), so legitimate first-party assemblies are stamped consistently; (c) if a third-party `GameKit.X` assembly is loaded that stamps a different version, the mismatch correctly fires — surfacing a real configuration drift, not a false positive. |
| T-06-02-SC | Tampering | npm/pip/cargo installs | accept | No npm/pip/cargo installs in this plan — only Core source-file additions. |
</threat_model>
