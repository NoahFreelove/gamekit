<objective>
Implement RANK-15: a leader-elected `RankDecayBackgroundService` that applies the Glicko-2 inactivity step (RD inflation, rating unchanged) to inactive players above a configurable rating threshold, stamps `last_decay_at`, and runs exactly once across replicas via a dedicated Redis lease key (`gamekit:rankings:decay:lease`).

Purpose: leaderboard hygiene — long-inactive high-rated players get rising RD (uncertainty) without unfair point loss, exactly as Glicko-2's "no games played" period update prescribes. The dedicated lock key prevents the decay runner from starving against the ticker lease.

Output: the decay lease helper, the background service, the `AddDecayInfrastructure` registration wired into `AddRankings`, and a Testcontainers integration test proving RD inflation + leader election + dedicated lock key.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| replica ↔ replica (Redis) | Multiple app replicas must not run the decay job concurrently — Redis lease serializes leadership |
| decay job → player_ranks | The only writer of RD during decay; a scale error or a rating write would corrupt every decayed player |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-08-02-02 | Denial of Service | decay job across replicas (double-run) | mitigate | Dedicated Redis lease `gamekit:rankings:decay:lease` (distinct from ticker lease); LockTtlSeconds=120 natural expiry; Polly backoff prevents Redis hammering; leader-election integration test |
| T-08-02-03 | Denial of Service | decay lock starvation vs ticker | mitigate | Decay uses its OWN key — long ticker drains can no longer block decay acquisition (Pitfall 4); test exercises both keys to prove non-collision |
