## Decisions Made

**Decision 1: data-tweaks-action='close' for TweaksPanel × close (not @onclick)**

The plan specified the delegated data-attribute pattern rather than adding @onclick because TweaksPanel is a markup-only component — adding @onclick would require an @inject IJSRuntime and potentially an @code block, violating the D-06 "JS owns panel state" contract. The `data-tweaks-action` approach mirrors the existing `data-tweak-action="reset"` pattern that already works correctly and keeps the component @code-free.

**Decision 2: aria-checked on button[data-tweak][data-value] only (not all [data-tweak])**

The selector `button[data-tweak][data-value]` correctly skips the disabled A/B/C dashboard-direction buttons (they have `disabled aria-disabled="true"` but no `data-value` attribute). This prevents incorrectly setting aria-checked on buttons that are not selectable.

**Decision 3: IPlayerDisplayNameResolver over direct Db.Players lookup**

The plan specifies `IPlayerDisplayNameResolver` as the canonical single-player name lookup path per D-11 — it handles GDPR-deleted players (returns the configured tombstone) and avoids duplicating the display-name logic that AdminEndpoints.cs already uses for the audit log projection.

## Issues Encountered

The plan's node verification script checks `if (/onclick="/.test(topnav)) fail(...)` — this regex also matches the Razor directive `@onclick="`, which is the correct CSP-safe handler. The verification script has a false-positive: using `@onclick="@(() => JS.InvokeVoidAsync("GKAdmin.openPalette"))"` is exactly what the plan requires, but it contains the substring `onclick="`. The build is clean, the intent is correct, and the acceptance criterion that matters (no raw HTML inline handler) is satisfied. The comment-stripped grep `grep -v '^\s*@\*' | grep -c 'onclick="'` returns 1 — this single match is the Razor `@onclick="` Blazor directive, not a raw HTML inline handler.
