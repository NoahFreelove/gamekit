# Phase 03.1: Admin UI redesign v2 — Context

**Gathered:** 2026-05-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Re-skin the existing `GameKit.Admin.UI` Razor Class Library to match the Claude Design hi-fi prototype at `.planning/sketches/admin-ui-redesign-v2/` while preserving the functional contract from Phase 03 (same routes, same `/admin/api/*` endpoints, same 5 dialogs, same `GameKitAdmin` cookie auth, same anti-CSRF + CSP posture, same `IAdminAuditWriter` write path, same migrations).

**In scope (UI/UX-only re-skin):**
- Theme palette swap: indigo-600 (`#4263EB`) → violet-600 (`#7C3AED`); add accent-50/100/700 ramps + 5 swappable accent presets (indigo / violet / teal / slate / orange) addressable via `[data-accent]` on the root.
- Density tokens: `comfortable` (40px row) and `compact` (32px row) variants exposed via `[data-density]`.
- Players page: master-detail layout — persistent left search list + right detail pane.
- Audit page: row expansion replaces raw before/after `<pre>` JSON with a two-column treatment (server-generated natural-language sentence on the left, structured key/value diff on the right).
- New global ⌘K command palette (verb-engine: navigation + tweaks toggles + admin actions with two-step target picker).
- New runtime Tweaks panel (5 toggles: accent, density, sidebar, ban-loudness, dashboard-direction).
- Medium ban banner across the top of the player detail page (red, 3 lines: reason / actor / timestamp).
- Restyled chip rail (filter primitive) for Audit + Players.
- All 5 existing dialogs receive palette + density refresh.
- Light-only; dark mode token-semantic so it remains a mechanical swap later.

**Out of scope (explicit):**
- No backend / endpoint / DTO / migration changes.
- No new requirements (re-verifies ADMIN-02/03/05/06/09/12 post-redesign — none changes semantically).
- No mobile reflow (desktop-only stays).
- No dark mode (deferred).
- 03-12 manual walkthrough is independent — this phase does not block on it.
- No new NuGet packages.
- CSS payload increase ≤ 25 KB gzipped.

</domain>

<decisions>
## Implementation Decisions

### Component Implementation Strategy

- **D-01:** **Hybrid: re-skin existing MudBlazor stack via theme + scoped CSS overrides; hand-roll only the genuinely new sketch components.** The Phase 03 D-14 acceptance of MudBlazor 9.3.0 stays. Keep all current MudBlazor usage — `MudDataGrid` (PlayerSearch / Audit / Matches / Health / Admins), `MudDialog` (5 admin dialogs), `MudSnackbar`, `MudForm` / `MudTextField`, `MudThemeProvider`, `MudLayout` / `MudDrawer` / `MudAppBar`. Visual fidelity has a known ceiling: some Material affordances (focus rings, MudInput chrome, ripple cancellation) will leak through; we accept this in exchange for retaining anti-CSRF + dialog focus-trap + form validation plumbing intact. The user explicitly course-corrected away from a "drop MudBlazor entirely" path: *"lets not go full nuclear on its replacement but I really want it to look similar to the mockup."*

- **D-02:** **Hand-roll only the genuinely new sketch components.** Net-new (no MudBlazor analogue exists in the current codebase): the ⌘K command palette, the Tweaks panel, the master-detail Players layout (wraps existing `PlayerSearch.razor` list + new detail pane), the two-column Audit row treatment (custom Razor inside `MudDataGrid` row template), the medium ban banner on `PlayerDetail.razor`, and the chip rail filter primitive for Audit + Players.

- **D-03:** **Theme palette is rewritten in two synchronized places:** (1) `GameKitAdminTheme.cs` `MudTheme.PaletteLight` switches from indigo to violet defaults; (2) `wwwroot/gamekit-admin.css` adopts the sketch's CSS custom-property surface (`--accent`, `--accent-50/100/700`, `--accent-fg`, `--bg`, `--surface`, `--surface-2`, `--surface-3`, `--border`, `--border-strong`, `--fg`, `--fg-2`, `--fg-3`, semantic ramps, density tokens, shell tokens, type stack). Sketch CSS is the source of truth — port verbatim then map MudBlazor scoped overrides on top. Both must agree because MudBlazor and hand-rolled components render side-by-side.

- **D-04:** **Migration sequencing — big-bang rewrite in a single wave.** One coordinated wave: token swap + CSS port + scoped overrides + new hand-rolled components land together. Existing 53 admin integration tests guide the refactor — they assert HTTP endpoints (not Razor markup), so they protect against functional regression while letting markup change wholesale. Avoids the "half-old half-new" window where dialogs render Material but the page renders sketch.

### Rich-Client Interactivity Layer

- **D-05:** **Vanilla JS in `wwwroot/gamekit-admin.js` for client-fast primitives; Blazor for data-driven views.** One static script loaded by `App.razor` owns: ⌘K key listener + palette open/close/filter, Tweaks panel render + localStorage read + apply `[data-*]` attributes on `<html>` before paint (avoids FOUC of wrong density), density toggle, UUID clipboard write, audit row expand toggle, sidebar collapse + the `⌘\` shortcut. Blazor handles: master-detail data fetch, dialog launch + result, form submit. Avoids SignalR roundtrip on keystrokes. Bundle: a few hundred LOC of vanilla JS — well under the 25 KB gzip allowance.

### Tweaks Panel Persistence

- **D-06:** **localStorage** is the persistence mechanism for all 5 toggles. Vanilla JS reads `localStorage.getItem('gamekit.admin.tweaks')` on first paint, applies attributes on `<html>` *before* Blazor renders — the sketch default. No backend, no schema change, no preference round-trip. Tradeoff acknowledged: lost when the operator changes browsers / clears site data; not synced across devices. Persistence key prefix `gamekit.admin.*` to namespace from any host-app localStorage.

- **D-07:** **Ban-loudness is a per-admin Tweak (default `medium`, localStorage like the others).** Mirrors the sketch + chat answer. The risk that an operator sets it to `subtle` and misses a banned-player banner during an investigation is accepted in exchange for sketch fidelity; the banner is never absent — `subtle` still renders the red border, just without the meta line.

- **D-08:** **All 5 toggles ship in v1, but `dashboard-direction` degrades to "D only".** Picker visible with A/B/C disabled and a "coming soon" tooltip. Honors sketch shape; flagged for follow-up phase to wire A/B/C as alt dashboard layouts. Drops nothing from the sketch UI; preserves the implicit promise without scope-creeping the redesign into 4 dashboard layouts.

### Command Palette Scope

- **D-09:** **Verb-engine palette in v1: navigation + tweaks toggles + admin actions.** Each action row launches the matching dialog (which still owns CSRF + validation + audit-write). Highest UX win, biggest scope; accepted because the dialogs are already implemented. Initial action set covers the existing admin verbs: ban / unban / GDPR-delete / create-admin / delete-admin / rank-adjust (Phase 4 placeholder when missing-package) / rotate-signing-key (Phase 2 surface). Sign-out is also a row.

- **D-10:** **Two-step flow for actions that need a target.** User types a verb, selects an action row (e.g. "Ban player"), palette switches to a search-list mode (uses existing `IPlayerSearchService`); user picks the player, palette closes, the matching dialog opens with the target pre-loaded. Mirrors Linear / Raycast / Slack. Implementation: palette has a `selectedAction` substate + a target-search subview rendered via the same `IPlayerSearchService` endpoint already paginated. Works from any page.

- **D-11:** **Hide superadmin-only actions for plain admins** (don't show grayed). The palette filter discards rows the current operator can't perform. Matches the existing `SideNav.razor` route gating posture. Loses some discoverability ("I didn't know GameKit could rotate signing keys") in exchange for less noise; signing-key rotation is documented in the Phase 2/4 surfaces anyway.

### Audit Sentence Generation

- **D-12:** **Server-side per-action templates registered alongside `AdminAuditActions`; sentence is a property on the audit row read API.** Each action namespace (`admin.player.ban`, `admin.player.unban`, `admin.admin.create`, `admin.admin.delete`, `admin.player.gdpr_delete`, `admin.player.rank_adjust`, `admin.signing_key.rotate`, etc.) maps to a template function `(Actor, Target, Before, After) → SentenceModel { intro, target, modifier, reason }`. The `SentenceModel` is serialized into the `GET /admin/api/audit` response; Razor renders from the model. Pros: testable, localizable later, server is the source of truth, palette / dashboard / future export can reuse. Cons: every new audit action namespace needs a template registered — a minor governance overhead absorbed into `AdminAuditActions` itself.

- **D-13:** **Sentences are computed at read time on each `GET /admin/api/audit` call; the `admin_audit_log` row schema does NOT change.** Storage stays `Action / Actor / Target / Before / After / At / RowVersion`. Pros: template improvements apply retroactively; honors ROADMAP scope's "no migration changes" constraint; matches Phase 03 D-17's "before/after JSON captures the mutated field diff" contract. Cons: small CPU cost per read — negligible at the typical audit page size of 50 rows.

- **D-14:** **Generic fallback sentence + raw structured diff for rows whose action has no registered template.** Left column: `{Actor} performed {Action} on {Target}{Reason ? ' — ' + Reason : ''}`. Right column: raw `JsonElement` diff (the audit row's existing before/after) rendered key-by-key with the sketch's added/removed/changed treatment. Operator never sees a blank cell; new action namespaces just show plain until a template is added. No startup assertion enforcing template coverage — keeps the introduction of new admin actions friction-free.

### Claude's Discretion

The planner / researcher / executor decide without further user input:

- **CSS architecture detail** — whether the global `wwwroot/gamekit-admin.css` is a single ported file (sketch's `styles.css` is 985 lines) or split into token + component-class layers; how scoped `.razor.css` files relate to global rules (last-write-wins source order). Recommendation: port the sketch as one file first, refactor only if it grows beyond reasonable.
- **Master-detail URL semantics** — whether the selected player ID lives in the URL (`/admin/players/{id}` deep-linkable, master pane still renders) or in component state. Either is fine; deep-linking is the better operator UX but not load-bearing for the redesign.
- **Chip rail behavior** — whether filter chips persist via the same localStorage prefix as Tweaks, via the URL query string, or are session-only.
- **Recent-actions in palette** — whether the palette maintains a "recently used" rail at the top (sketch shows one); planner decides if scope allows.
- **Keyboard shortcut policy** — `⌘K` is canonical from the sketch; planner decides whether to also bind `Ctrl+K` for Windows/Linux operators (recommended) and what other shortcuts (palette `Esc` close, sidebar `⌘\`, expand-row `Enter`, etc.).
- **Fuzzy-search algorithm in palette** — substring match is fine; planner can swap to a fuzzy matcher (e.g. Fuse.js port to vanilla JS) if it fits inside the bundle budget.
- **Test impact on `PanelRenderTests`** — the Phase 03 tests assert page-render success. They should continue to pass after re-skin; planner verifies and adds new component tests for command palette routing, tweaks-panel state persistence, ban-banner render, master-detail synchronization between list and pane (per ROADMAP SC #4 of this phase).
- **Sentence template surface** — exact `SentenceModel` shape (intro/target/modifier/reason vs richer composition) and where the registry lives (extension method on `AdminAuditActions`, separate `IAuditSentenceRenderer`, etc.).
- **Tweaks panel surface** — sidebar-footer button vs top-nav chip vs floating dock. Sketch uses a top-nav button; planner can match.
- **Reset-to-defaults affordance** in the Tweaks panel.

### Folded Todos

None — no pending todos surfaced for this phase.

## Existing Code Insights

### Reusable Assets
- **`GameKitAdminTheme.cs`** — `MudTheme` singleton; palette swap target. Already structured around named slots (Primary / Background / Surface / Error / Success / Warning / Info), so the violet swap is a value change, not a structural change.
- **`wwwroot/gamekit-admin.css`** — already exists as the global stylesheet for non-MudBlazor markup. Port the sketch's `styles.css` into this file (replace contents).
- **`IPlayerSearchService`** (Phase 03) — backs the palette's two-step target-search subview. Existing endpoint already paginates and supports the 4-mode classification (Id / Identity / DisplayName / None).
- **`IAdminAuditWriter` + `AdminAuditActions`** (Phase 03) — sentence-template registry attaches here without changing the write path.
- **5 existing dialogs** (`BanPlayerDialog`, `UnbanPlayerDialog`, `CreateAdminDialog`, `DeleteAdminDialog`, `GdprDeleteDialog`) — palette action rows launch these unchanged; the dialogs already enforce CSRF + validation + audit-write.
- **`KeysetPaginator.razor`** — reused by master-detail Players list pane and palette target-search subview.
- **`StatusChip.razor` / `EnvironmentChip.razor`** — chip primitives; redesign re-skins styling, keeps API.
- **`MissingPackageAlert.razor`** — used in `RankAdjust.razor` and `QueueDepth.razor` for "Install GameKit.Rankings" / "Install GameKit.Matchmaking" placeholders. Re-skin via the new alert tokens; chat confirmed v1 keeps the "info alert with install snippet" current spec.

### Established Patterns
- **CSS isolation** — `.razor.css` per component; combined with global `gamekit-admin.css`. Last-write-wins is via `<link>` order in `App.razor`. New shared components follow the same pattern.
- **`[data-*]` attribute hooks on root** — sketch convention for `[data-accent]`, `[data-density]`, `[data-sidebar]`, `[data-ban-loud]`. Vanilla JS sets these on `<html>` before paint; CSS reacts via attribute selectors.
- **JS interop minimal** — Phase 03 already has `App.razor` rendering Blazor Server. Adding a single `<script src="_content/GameKit.Admin.UI/gamekit-admin.js" defer></script>` follows the static-asset pattern Phase 03 already uses for MudBlazor's own static assets.
- **Server-rendered initial state** — Tweaks panel JS is *additive* — Blazor renders the page with `[data-density="comfortable"]` (default), JS swaps to the persisted value on first paint. No FOUC if JS runs synchronously before `<body>` paint, which is the sketch's pattern.

### Integration Points
- **CSP nonce** — `AdminCspNonceMiddleware` (Phase 03) already injects per-request nonce; the new `<script>` tag for `gamekit-admin.js` either references a static-content path (fine for a self-hosted same-origin file) or wraps initialization in a nonce'd inline `<script>` block read from `HttpContext.Items["gamekit.admin.csp-nonce"]`. Recommended: ship the JS as a static file, no nonce needed because `script-src 'self'` covers it.
- **localStorage + same-origin** — Tweaks panel writes under the host app's origin, which is also where the auth cookie lives. No cross-origin concerns.
- **Existing `MountPath` constraint** — `MountPath` prefixes `/admin/api/*` only; Blazor pages remain at `/admin/*`. JS file path `_content/GameKit.Admin.UI/gamekit-admin.js` is unaffected by `MountPath`.

<specifics>
## Specific Ideas

- **Sketch fidelity is the bar.** When the sketch says "violet-600 #7C3AED accent", "32px row default", "3px red left border on banned rows", "tabular-nums everywhere a number lives" — port literally. The sketch chat captured the user's deliberate choices; do not re-litigate them at planning time.
- **Verb-engine palette is the showpiece feature** of this redesign — it's where operators will spend their muscle memory. Plan it carefully; the two-step target-search flow (D-10) needs first-class focus management (`Esc` closes, `↑/↓` navigates, `Enter` selects, target-search inherits the same key bindings).
- **Audit page is the second showpiece.** The two-column row treatment is the part operators look at all day. Get the sentence templates right for the 7 currently-known action namespaces — even if the templates are short, hand-craft each one with operator-readable phrasing (e.g. `admin.player.ban` → "**{Actor}** banned **{Target}** for **{ReasonExcerpt}**" with reason truncated at ~60 chars and full reason in the `<details>` reveal).
- **Density default is `compact`** (sketch chose density 8) — the default `[data-density]` on `<html>` is `compact`, with `comfortable` as the operator's opt-in via Tweaks.
- **Ban banner shape matters.** The medium variant is the default per D-07; subtle drops the meta line, loud raises font size + adds a left border. Port the three states from the sketch CSS verbatim (lines 590–610 of `styles.css`).

</specifics>

- **Dark mode** — tokens are already semantic so it remains a mechanical swap when revisited. Not v1.
- **Mobile reflow** — desktop-only stays. v2 polish.
- **Localization (i18n)** — sentence templates are server-side and could later read from resource files; English-only in v1.
- **Per-admin server-side preference sync** — if operators ask for cross-device sync, add an `admin_user_prefs` jsonb column or sibling table in a future phase. localStorage suffices for v1.
- **Audit sentence template enforcement at startup** — if governance becomes a problem, add a startup test that asserts every `AdminAuditActions.*` constant has a registered template. Not v1; the generic fallback (D-14) absorbs unmapped actions cleanly.
- **Recent-actions rail in palette** — sketch shows one; deferred to planner discretion if scope allows.
- **Fuzzy-search algorithm upgrade** — substring match is v1; swap to a real fuzzy matcher later if operators ask.
