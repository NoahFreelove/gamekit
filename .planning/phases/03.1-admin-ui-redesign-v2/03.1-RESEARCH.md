# Phase 03.1: Admin UI redesign v2 — Research

**Researched:** 2026-05-01
**Domain:** Blazor Server re-skin (MudBlazor theme + scoped CSS + vanilla JS interop)
**Confidence:** HIGH

## Summary

This is a presentation-only re-skin of an already-shipped Razor Class Library. Every load-bearing scope decision (D-01 through D-14) was locked in CONTEXT.md and is treated as non-negotiable here. The research below answers the *operational* questions a planner needs but CONTEXT does not pin down: concrete CSS payload numbers, file load order under .NET 10 CSS isolation, the existing CSP-nonce threading point in `App.razor`, the MudBlazor 9.3 palette-override surface and known leakage points, the JS↔Blazor handoff for the verb-engine palette's two-step flow, and a Nyquist validation matrix for SC #1–#6.

**Primary recommendation:** Land the redesign as a single big-bang wave (per D-04) anchored on five new shared components (`CommandPalette`, `TweaksPanel`, `BanBanner`, `ChipRail`, `MasterDetailLayout`) plus one vanilla JS file (`wwwroot/gamekit-admin.js`) plus a verbatim port of the sketch's `styles.css` into `wwwroot/gamekit-admin.css`. Bundle math is comfortable: the sketch CSS is +5.2 KB gzip vs the existing 1.3 KB baseline (current 1339 B gzip → ported 6581 B gzip), well under the 25 KB allowance.

### Pattern 1: MountPath scope (carryover — DO NOT VIOLATE)

**What:** `GameKitAdminOptions.MountPath` (default `/admin`) prefixes only the admin **HTTP API** (`/admin/api/*`). Blazor `@page` routes stay at `/admin/*` regardless. Static-asset paths under `_content/GameKit.Admin.UI/*` are root-relative and unaffected.

**Source:** `src/GameKit.Admin.UI/Middleware/AdminCspNonceMiddleware.cs:56` (`Path.StartsWithSegments(_adminPrefix)`); `src/GameKit.Admin.UI/Builder/AdminBuilderExtensions.cs` (cookie-options conditional); `src/GameKit.Admin.UI/Http/AdminFormEndpoints.cs:*` (multiple `$"{opts.MountPath}/login..."` redirects); 03-UI-SPEC.md Route scope note (revision 2026-04-18).

**Implication for redesign:**
- `gamekit-admin.js` is loaded from `_content/GameKit.Admin.UI/gamekit-admin.js` (root-relative). MountPath does not affect it.
- Palette navigation rows MUST emit Blazor `NavigationManager`-friendly URLs starting with `/admin/...` (NOT `${MountPath}/...`). The Blazor router lives at `/admin/*` always.
- Palette ⌘K listener MUST attach `keydown` on `window` regardless of URL — the listener is browser-global, not path-scoped. (CSP `frame-ancestors 'none'` already prevents the admin page from rendering inside another origin's frame, so there's no risk of the listener firing in a hostile context.)

### Pattern 2: CSS isolation load order under .NET 10

**What:** Blazor compiles every `.razor.css` file into a per-component fragment with a `b-{HASH}` attribute selector, then bundles them into `obj/{Configuration}/{TFM}/scopedcss/projectbundle/{AssemblyName}.bundle.scp.css`. The RCL bundle is **`@import`-ed at the top** of the consumer app's `{AssemblyName}.styles.css`. The `<head>` `<link>` references that styles file via `@Assets["..."]`.

**Source:** [CITED: learn.microsoft.com/aspnet/core/blazor/components/css-isolation?view=aspnetcore-10.0] — "the RCL's stylesheet is imported at the top of the app's stylesheet: `@import '_content/ClassLib/ClassLib.bundle.scp.css';`". Bundle artifact verified at `obj/Debug/net10.0/scopedcss/projectbundle/GameKit.Admin.UI.bundle.scp.css`.

**Predictable last-write-wins recipe for this redesign:**

| Layer | Source order | Selector specificity | Net result |
|-------|-------------|----------------------|------------|
| 1 | `MudBlazor.min.css` (linked first in `App.razor:24`) | `.mud-button` (0,1,0) | Material baseline |
| 2 | `{Asm}.bundle.scp.css` (linked second; contains all `.razor.css` rules) | `.foo[b-XXXX]` (0,2,0) | Component scoped overrides — **wins on specificity vs un-scoped** |
| 3 | `gamekit-admin.css` (linked third in `App.razor:26`) | `.foo` (0,1,0) | Loses to scoped (lower specificity) but wins vs MudBlazor (later source) |

**Critical mismatch:** When the global `gamekit-admin.css` and a `.razor.css` rule target the SAME element, the **scoped version always wins** (specificity +10 from `[b-XXXX]`). The redesign exploits this — global tokens (`--accent`, `--bg`, etc.) live in `gamekit-admin.css`; per-component MudBlazor overrides (`.mud-button.btn-primary` etc.) live in `.razor.css` files where they need to bypass MudBlazor's defaults via specificity.

**Pattern: always use CSS custom properties, not literal hex, for swappable tokens.** A `.razor.css` rule that wants the violet accent writes `background: var(--accent)` — no need to override hex. The Tweaks panel changes `[data-accent]` on `<html>` and every dependent `var(--accent)` re-resolves automatically.

**Example:**

```css
/* Source: learn.microsoft.com/aspnet/core/blazor/components/css-isolation */
/* gamekit-admin.css — global */
:root { --accent: #7C3AED; }
[data-accent="indigo"] { --accent: #4263EB; }

/* CommandPalette.razor.css — scoped */
/* Compiles to: .palette[b-X] { background: var(--surface); border: 1px solid var(--border); } */
.palette { background: var(--surface); border: 1px solid var(--border); }
```

### Pattern 3: MudBlazor 9.3 palette override discipline

**What:** `MudThemeProvider` reads `MudTheme.PaletteLight` at render time and writes a `<style>` block of `--mud-palette-*` CSS custom properties on its host element. MudBlazor's own component styles consume those variables (`.mud-button-primary { background: var(--mud-palette-primary); }`).

**Source:** [CITED: github.com/MudBlazor/MudBlazor/discussions/5588] — `MudTheme` palette pattern; [CITED: deepwiki.com/MudBlazor/MudBlazor/7.2-theming-system] — "MudThemeProvider uses a StringBuilder to convert theme properties into CSS custom properties, with palette variables prefixed with `--mud-palette-`".

**Recipe for the violet swap:**

1. Edit `GameKitAdminTheme.cs` (file already exists):
   ```csharp
   PaletteLight = new PaletteLight
   {
       Primary = "#7C3AED",        // violet-600 (was #4263EB)
       PrimaryDarken = "#6D28D9",  // accent-700
       PrimaryLighten = "#F5F3FF", // accent-50
       // ... all other slots map 1:1 to sketch tokens
   }
   ```
2. The `gamekit-admin.css` global file owns the `--accent`, `--accent-50`, `--accent-700` custom properties separately from MudBlazor's `--mud-palette-*`. **Both must agree on hex.**

**Known-leaky surfaces (acknowledged in D-01) and the pinpoint workarounds:**

| Leak | Why it happens | Workaround |
|------|---------------|------------|
| MudBlazor focus ring | MudBlazor uses `box-shadow: 0 0 0 2px var(--mud-palette-primary)` on focused inputs; doesn't read our `--accent` | Sketch `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }` (lines 977–979 of styles.css) — global rule wins on `:focus-visible` because MudBlazor uses `:focus`. Verify in §Accessibility |
| MudBlazor ripple | MudBlazor injects an inline `<span>` ripple via JS with hard-coded hex via `--mud-palette-action-default` | Override the variable in `gamekit-admin.css`: `.gk-admin-root { --mud-palette-action-default: var(--accent); }` |
| MudInput chrome (underline / hover border) | MudInput wraps with `border-bottom: 2px solid var(--mud-palette-primary)` | Override `--mud-palette-primary` directly in `gamekit-admin.css` to be SAME hex as `--accent` (or set up the MudTheme to track our token — preferred). The MudTheme path is cleaner |
| MudTabs indicator color | Inherits from primary | Same — `--mud-palette-primary` propagates |

### Pattern 4: `[data-*]` attribute application BEFORE first paint

**What:** Without intervention, Blazor SSR pre-renders HTML at the default density/accent, the page paints with that, then JS runs and switches the attributes — visible flash. To eliminate FOUC, the script that reads localStorage and sets `<html data-density="..." data-accent="...">` MUST run synchronously **inside `<head>`** before `<body>` begins parsing.

**Source:** [VERIFIED via codebase] `App.razor:17–28` shows the `<head>` block. Currently no inline `<script>` is present in `<head>` — only the `<link rel="stylesheet">` triplet.

**Recipe:**

```razor
@* App.razor (mutated head section) *@
<head>
    ...
    <link rel="stylesheet" href="_content/GameKit.Admin.UI/gamekit-admin.css" />
    <HeadOutlet />
    @* NEW — runs synchronously, applies [data-*] to <html> before <body> paints *@
    <script nonce="@Nonce">
      (function() {
        try {
          var t = JSON.parse(localStorage.getItem('gamekit.admin.tweaks') || '{}');
          var html = document.documentElement;
          html.setAttribute('data-accent',   t.accent   || 'violet');
          html.setAttribute('data-density',  t.density  || 'compact');
          html.setAttribute('data-sidebar',  t.sidebar  || 'expanded');
          html.setAttribute('data-ban-loud', t.banLoud  || 'medium');
        } catch (e) { /* corrupt JSON — apply defaults */ }
      })();
    </script>
</head>
```

**Critical:** The inline `<script>` MUST carry `nonce="@Nonce"` because the existing CSP policy emitted by `AdminCspNonceMiddleware.cs:76` is `script-src 'self' 'nonce-{nonce}'`. Inline scripts without the nonce are blocked. The nonce is already wired into `App.razor:50` via `@Nonce` (reads `HttpContextAccessor.HttpContext?.Items[AdminCspNonceMiddleware.NonceItemKey]`). The new inline block reuses that same expression — no new nonce plumbing needed.

**Recommendation: single IIFE with one window-attached namespace.**

**Why IIFE:**
1. CSP `script-src 'self' 'nonce-...'` does NOT include `'strict-dynamic'` or module-script-src. An ES module would still load (`<script type="module" src="..."` is `script-src`-covered) but the indirect `import()` calls would each need additional CSP allowances. IIFE avoids this entirely.
2. The vanilla JS is ~300-500 LOC; module boundaries are overkill for this size.
3. `defer` attribute on `<script src="…/gamekit-admin.js" defer>` ensures the file runs after parsing but before `DOMContentLoaded` — same effective timing as a module.

### Anti-Patterns to Avoid

- **Hand-rolling clipboard copy without `navigator.clipboard.writeText()` fallback.** Older Safari needs `document.execCommand('copy')`. The sketch uses `navigator.clipboard.writeText()` with a `try/catch` ([CITED: primitives.jsx:48]); replicate the try/catch.
- **Forgetting CSP nonce on the inline tweaks-init `<script>`.** It will silently fail under the strict CSP and the page paints with default density (FOUC). The nonce is mandatory.
- **Putting Blazor route paths into the JS palette.** Use `/admin/...` literals; do NOT prefix with `${MountPath}` because the Blazor router lives at `/admin/*` regardless of MountPath.
- **Letting MudBlazor's default ripple color leak.** Override `--mud-palette-action-default` in `gamekit-admin.css` (or via the C# theme) so it tracks `--accent`.
- **Using `display: none` to hide superadmin actions in the palette (D-11).** The list MUST be filtered before render so the row never appears in the DOM — otherwise `Tab` cycles through hidden rows and `aria-` semantics confuse screen readers. Use `if (currentUserRole !== 'superadmin') skip` in the JS filter.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CSRF token validation in palette → dialog flow | Custom token cache in JS | Existing `AntiforgeryValidationFilter` on the dialog's POST handler | Dialog already POSTs with the antiforgery cookie+header through the existing pipeline; JS palette only opens the dialog, doesn't bypass it |
| Player search inside the palette target-search subview | New JS-side fuzzy index | `IPlayerSearchService` via `GET /admin/api/players/search?query=X` | Already paginated, already classified (4-mode), already authorized via cookie. The JS palette `fetch()`-es it with `credentials: 'same-origin'` |
| Audit sentence localization | Per-locale string table | Server-side template registry (D-12) — English-only in v1 | Token-semantic; resource files are an i18n surface to add later |
| Master-detail "keep state across navigation" | Custom client cache | URL parameter (`/admin/players/{id?}`) | Browser already has a back-button + bookmark-able URL; the master list re-uses the SAME page so the search results are not disposed |
| Blazor-side JS bundling (e.g. WebOptimizer) | Build-time ESBuild step | Hand-authored `gamekit-admin.js` (~300-500 LOC) served as static asset | At this size, a build step is more dependency than benefit. The file is small enough to read in one pass |

**Key insight:** This phase is intentionally low on new abstractions. The only NEW server-side concept is the sentence-template registry (D-12). Every other "new" file is a hand-rolled Razor component using existing service and dialog infrastructure unchanged.

## Common Pitfalls

### Pitfall 1: FOUC of wrong density on first paint

**What goes wrong:** Page renders with the SSR'd default `[data-density="comfortable"]`, then JS runs after `DOMContentLoaded` and switches to the persisted `compact` value. Visible flash, especially noticeable on the master-detail layout where row heights jump.

**Why it happens:** Default `<script>` with no `defer`/`async` blocks parsing but doesn't run until the surrounding `<head>` finishes. Default `<script src=...>` (without `defer`) DOES run during head parse but only after the file downloads. `defer` runs the script after document parse (after first paint potentially). Async runs whenever — also after first paint.

**How to avoid:** The data-attribute apply MUST be an INLINE `<script nonce="@Nonce">…</script>` placed in `<head>`, BEFORE the `<HeadOutlet />` and BEFORE the `<body>` opens. localStorage reads are synchronous; the entire init block runs in <1 ms.

**Warning signs:** Visible flash when reloading. The first SSR'd HTML response has `<html>` with no `data-*` attributes; the post-paint state has `data-density="compact" data-accent="violet"`.

### Pitfall 2: MudBlazor scoped CSS rule leaks across the violet swap

**What goes wrong:** A `MainLayout.razor.css` rule like `.gk-content { background-color: var(--gk-color-bg); }` (line 8 of the existing file) survives the redesign because the `--gk-color-*` legacy custom properties stay defined as aliases. Then a new `.razor.css` rule sets `background: var(--bg)` and the two compete.

**Why it happens:** The redesign keeps existing `.razor.css` files for backward compatibility but adds new ones with sketch tokens. Two custom-property namespaces co-exist: legacy `--gk-color-*` and new `--accent`/`--bg`/etc.

**How to avoid:**
- **Rewrite `gamekit-admin.css` from scratch** using only the sketch tokens. DELETE `--gk-color-*`, `--gk-space-*`, `.gk-viewport-warning`.
- **Audit every existing `.razor.css` file** (`MainLayout.razor.css:9`, `LoginLayout.razor.css`, etc.) and replace `var(--gk-color-…)` with `var(--…sketch-token…)`.
- One single grep in the planner's verification step: `git grep '--gk-color-\|--gk-space-' src/GameKit.Admin.UI/` should return zero matches after the redesign lands.

### Pitfall 3: ⌘K listener fires inside MudInput edit fields

**What goes wrong:** Operator types `K` while ⌘ held inside a textarea (e.g. ban-reason input); the palette opens and steals the keystroke.

**Why it happens:** Naïve `window.addEventListener('keydown', ...)` ignores the focus target.

**How to avoid:** Check `e.target.tagName !== 'INPUT' && e.target.tagName !== 'TEXTAREA'` before opening. **Exception:** ⌘K is the canonical "open command bar" gesture and Linear/Notion DO open the palette even from inside text fields. The right answer is to **always** open on ⌘K but **always** call `e.preventDefault()` and capture the keystroke. The ban dialog's textarea will lose focus to the palette; user closes palette with Esc and focus returns. Document this as expected.

### Pitfall 4: Antiforgery cookie not present on JS-initiated POSTs

**What goes wrong:** Palette → ban dialog flow looks correct, but the POST to `/admin/api/players/{id}/ban` returns `400 csrf_validation_failed`.

**Why it happens:** The dialog renders inside the Blazor circuit; `<form>` markup is hydrated by Blazor. Blazor Server forms ship the antiforgery token in a hidden input automatically (`Microsoft.AspNetCore.Components.Forms.AntiforgeryToken`). If the planner re-implements the dialog as a JS-rendered overlay (it won't — D-02 says hand-roll only what's NOT already a MudBlazor analogue, and dialogs ARE), the antiforgery token must be threaded manually via the `gk_admin_csrf` cookie + `X-GameKit-Admin-CSRF` header.

**How to avoid:** Don't re-implement the dialogs. The 5 existing `Dialogs/*.razor` files render via `IDialogService.ShowAsync<T>` → a `MudDialog` that posts via Blazor's antiforgery-aware fetch wrapper (or directly via the CSRF cookie's double-submit pattern). The palette only LAUNCHES the dialog; the dialog still does the POST.

### Pitfall 5: Bundle size regression from accidentally including MudBlazor's full CSS variable surface

**What goes wrong:** A planner who reads "MudBlazor 9.3 emits all `--mud-palette-*` variables at runtime" decides to override all of them in `gamekit-admin.css` — adds 50+ overrides, blows the gzip budget.

**Why it happens:** MudBlazor exposes ~120 palette + spacing tokens. Most don't need overriding; the violet swap only affects `Primary`, `PrimaryDarken`, `PrimaryLighten` and a handful of derived tokens.

**How to avoid:** Set the palette in the C# `MudTheme` (5-10 properties), do NOT redeclare those in `gamekit-admin.css`. The `gamekit-admin.css` file owns ONLY the sketch tokens (`--accent`, `--bg`, `--surface`, etc., ~30 vars total). Audit by grep: `grep -c 'var(' wwwroot/gamekit-admin.css` should be ≤ 200.

### Pitfall 6: The static-SSR Login page renders without the inline tweaks-init script

**What goes wrong:** Login.razor (line 31 in App.razor handling) is decorated with `[ExcludeFromInteractiveRouting]` and renders as static SSR. If the inline tweaks `<script>` lives only inside an interactive component, it doesn't run on the login page; user sees indigo accent on login → violet on dashboard.

**Why it happens:** The script must be in `App.razor`'s `<head>`, which ALL pages share regardless of rendermode.

**How to avoid:** Place the inline init `<script>` directly in `App.razor` `<head>`, not in `MainLayout.razor`. (`App.razor` is the only file emitted by every admin response — both static-SSR and interactive.) Verify by reading `App.razor:17-28` — the head block is identical for both rendermodes.

### Known Threat Patterns for Blazor Server + vanilla JS

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XSS via Razor interpolation of user-supplied audit reason | Tampering | Razor `@reason` interpolation auto-HTML-encodes. Sentence templates use C# string interpolation — verify they do NOT call `@((MarkupString)...)`. The 7 currently-known templates have no markup output |
| XSS via JS palette injection of player display name | Tampering | The vanilla JS palette renders rows by setting `textContent` (not `innerHTML`) — required pattern; document explicitly in the JS file |
| CSP bypass via inline tweaks-init `<script>` | Tampering | Strict CSP `script-src 'self' 'nonce-{N}'` requires the nonce attribute on inline scripts; the bootstrap script uses `nonce="@Nonce"` — verified by `CspAndAntiforgeryTests.AdminResponse_Has_ContentSecurityPolicy_Header` continues to pass |
| Clickjacking the admin panel via iframe | Spoofing | `frame-ancestors 'none'` in CSP (existing) — unchanged |
| CSRF on dialog mutations | Tampering | `AntiforgeryValidationFilter` on every POST endpoint (existing); palette only LAUNCHES dialogs, dialog forms ship the antiforgery token |
| localStorage tampering — operator changes `data-density` to break layout | Tampering | Self-inflicted only; no security impact. The `try/catch` around the JSON.parse handles corrupt input by applying defaults |
| Information disclosure via `D-11` superadmin actions visible to admins | Information Disclosure | UI filter discards rows the operator can't perform (D-11). Server-side authorization is the canonical gate — `[Authorize(Policy = AdminPolicies.Superadmin)]` still rejects 403 if the JS UI were bypassed |
