## Summary

The four prior blockers from `03.1-REVIEW.md` are mostly resolved correctly:

- **BLOCKER-01 (CSP-blocked inline `onclick=`)** — fixed cleanly in both call-sites:
  `TopNav.razor:29` switched to `@onclick="@(() => JS.InvokeVoidAsync(...))"` (server-side
  Blazor handler — no inline-event CSP exposure), and `TweaksPanel.razor:30` adopted the
  delegated `data-tweaks-action="close"` pattern wired through the existing global click
  handler in `gamekit-admin.js:196-197`. No new inline event handlers introduced anywhere
  under review.
- **BLOCKER-02 (palette target search wrong JSON shape)** — `gamekit-admin.js:345-352` now
  drills into `page.items` with the correct defensive guard.
- **BLOCKER-03 (empty-string→Guid deserialization)** — defended on both sides: JS now
  passes the literal `00000000-0000-0000-0000-000000000000` zero-GUID
  (`gamekit-admin.js:306, 397-399`), and `MainLayout.OpenDialog` accepts `string targetId`
  with `Guid.TryParse` → `Guid.Empty` fallback (`MainLayout.razor:115-117`).
- **BLOCKER-04 (`nav.*` palette rows dispatch as dialogs)** — `AdminCommand` and
  `AdminCommandDto` gained a `Url` field; the registry populates `Url:` on every nav row;
  the palette JS branches on `commandId.indexOf('nav.') === 0` and routes via
  `window.location.href` to the server-trusted URL. The dropped `nav.player-detail` row
  is regression-guarded by `CommandPaletteTests.Registry_DoesNotContainPlayerDetailNavRow`.
- **WARNING-01 (Tweaks aria-checked never reflected)** — `gamekit-admin.js:82-89` now
  iterates `button[data-tweak][data-value]` and sets `aria-checked` based on the active
  value; covered by `TweaksPanelTests.TweaksPanel_AllOptionButtons_Carry_DataTweak_DataValue_RoleRadio`.
- **WARNING-02 (hardcoded `/admin/api/players/search`)** — `App.razor:39-55` now emits
  `window.GKAdminConfig = { apiBase: '@apiBase' }` from a nonced inline script using the
  resolved `MountPath`; the JS reads `window.GKAdminConfig.apiBase` with a defaultable
  fallback (`gamekit-admin.js:342`).

The CSP-strictness assertion (BLOCKER-01) holds in fact: I scanned the three Razor files
under review for any remaining `onclick=`, `onkeydown=`, `oninput=`, etc. — none present.
The two new `@onclick` lambdas in `TopNav.razor` are server-rendered Blazor handlers
(SignalR roundtrip), which CSP does not restrict.

**However**, the WARNING-06 fix in `PlayerDetailPane.LoadAsync` is **wrong** in a way that
re-introduces the same class of mis-attribution defect the fix was meant to close. The new
code resolves the banning-actor display name by calling `IPlayerDisplayNameResolver` on the
audit row's `ActorId`, but `ActorId` is an `AdminUser.Id` (admin table) and the resolver
queries the `players` table — every banning-admin id will miss in `players`, fall through
to `_opts.DeletedPlayerDisplayName` ("Deleted Player" by default), and the BanBanner will
falsely render "by **Deleted Player**" for every human-issued ban. The UX is strictly worse
than the prior "by **system**" hardcode because operators will now believe the banning
admin's account was deleted. Details and fix below — this is BLOCKER-grade because it
directly contradicts the success criterion of WARNING-06 and ships incorrect attribution
on the load-bearing red banner that surfaces during incident investigations.

The remaining issues are smaller: a Blazor anti-pattern (`ConfigureAwait(false)` in a
component method that subsequently calls `StateHasChanged`), several palette-registered
verbs that have no dialog handler and silently no-op on click (`sign-out`, `rank-adjust`,
`rotate-signing-key`), an XML-doc parameter-name drift on the `MatchHistoryRow` record, a
stale fetch race when a target search resolves after `closePalette()`, and a couple of
cosmetic untouched issues from the prior review (WARNING-03/04/05 + INFO-02/03/04/05) that
remain out of scope for the gap-closure plans.

## Blockers

### BLOCKER-GAP-01: `PlayerDetailPane._bannedByName` resolves an admin id against the players table — BanBanner falsely attributes every ban to "Deleted Player"

**Files:**
- `src/GameKit.Admin.UI/Components/Shared/PlayerDetailPane.razor:264-274`
- `src/GameKit.Core/Services/PlayerDisplayNameResolver.cs:32-50`
- `src/GameKit.Admin.UI/Entities/AdminUser.cs:13-19`

**Issue:**

The Plan 03.1-11 fix for WARNING-06 reads:

```csharp
var banRow = await Db.AdminAuditLog.AsNoTracking()
    .Where(r => r.Action == GameKit.Admin.UI.Services.AdminAuditActions.PlayerBan
                && r.TargetId == _player.Id)
    .OrderByDescending(r => r.CreatedAt)
    .ThenByDescending(r => r.Id)
    .Select(r => new { r.ActorId })
    .FirstOrDefaultAsync(ct).ConfigureAwait(false);
if (banRow is not null && banRow.ActorId.HasValue)
{
    _bannedByName = await PlayerNames.ResolveAsync(banRow.ActorId.Value, ct).ConfigureAwait(false);
}
```

`AdminAuditLog.ActorId` is the **admin user id** (`AdminUser.Id` from
`gamekit.admin_users`), per `AdminEndpoints.GetAdminId(http)` at line 496-503 + the
`actorId` argument threaded through every service call (`BanPlayerAsync` line 235;
`PlayerBanService.BanAsync` ultimately writes the row with `ActorId = actorId`).

`IPlayerDisplayNameResolver.ResolveAsync` queries `_ctx.Players.Where(p => p.Id == playerId.Value)`
exclusively (PlayerDisplayNameResolver.cs:41-46) and returns `_opts.DeletedPlayerDisplayName`
when no matching player row exists. Admins live in `gamekit.admin_users`, **never** in
`players` (AdminUser.cs:13: "Identity is separate from `players` — admin accounts never
overlap with player accounts"). Therefore every lookup of an admin id against the player
table will miss and return the configured deleted-player tombstone.

**Operator impact:** every human-issued ban now renders

> **Banned: <reason>**
> by **Deleted Player** · 2026-05-02 14:32:11 UTC

instead of the prior incorrect "by **system**" or the intended "by **<admin username>**".
This is strictly worse — operators will believe the banning admin's account was deleted
and start chasing a phantom audit-trail problem.

The same prior-review fix proposal called this out: "plumb `BannedById` through the entity
projection + resolve via `IPlayerDisplayNameResolver`" — but that proposal was wrong for
the same reason; `IPlayerDisplayNameResolver` is a **player** resolver, not an
admin-user resolver.

**Fix:** Resolve the admin's `Username` directly via the `AdminUser` table (no caching
strictly required — admin lookups are infrequent vs. player matches). Alternative B (b)
from the prior review — render `null → "unknown actor"` — is also acceptable but
strictly worse than truth-telling when the admin row exists.

```csharp
// In PlayerDetailPane.LoadAsync, replace the PlayerNames.ResolveAsync call with a
// direct lookup against admin_users; pre-cache via IMemoryCache if needed.
if (banRow is not null && banRow.ActorId.HasValue)
{
    _bannedByName = await Db.Set<AdminUser>().AsNoTracking()
        .Where(a => a.Id == banRow.ActorId.Value)
        .Select(a => a.Username)
        .FirstOrDefaultAsync(ct);
    // Falls through to "unknown actor" via the BanBanner consumer when the admin row
    // is gone (account hard-deleted or schema drift).
}
```

Add a regression test that (a) seeds an admin row + a player + an `admin_audit_log`
row with `ActorId = adminId`, then (b) renders `PlayerDetailPane` and asserts the
`<BanBanner ActorName="...">` parameter is the admin's username, not the
configured tombstone string. Without this test the same defect can regress unnoticed
because component tests today (`PlayersWorkspaceTests`) only stub the resolver.

## Warnings

### WARNING-GAP-01: `AdminCommand`/`AdminCommandDto` `Url` field is rendered into a `data-url=` attribute that the markup auto-encodes — but the JS assigns it to `window.location.href` without re-validation, opening a small `javascript:`-URL surface if the registry is ever populated from non-source data

**Files:**
- `src/GameKit.Admin.UI/wwwroot/gamekit-admin.js:289-294`
- `src/GameKit.Admin.UI/Services/AdminCommandRegistry.cs:51-59`

**Issue:** The current registry hardcodes every nav URL as a constant string literal in
source (`Url: "/admin"`, `Url: "/admin/players"`, …). With that contract — registry =
source-only constants — the assignment `window.location.href = url` is safe. But the
in-line comment at `gamekit-admin.js:285-288` argues correctness from "server-trusted
(sourced from AdminCommandRegistry, never operator input)" — which holds *today* but is
not enforced by anything. If a later plan moves the registry to the database (a plausible
path: D-09 mentions "minor governance overhead absorbed into AdminAuditActions") or allows
a host app to register commands via `AddGameKitAdmin().AddCommand(...)`, an attacker who
can write the `Url` column / call the extension could inject `javascript:fetch(...)` and
get free same-origin code execution against any admin who opens the palette.

This is defense-in-depth; today's exposure is zero. Worth fixing now while the surface is
small.

**Fix:** Validate the URL in JS before assignment. Either parse with `new URL(url, location.origin)`
and reject non-http(s) schemes, OR (simpler) require the URL to start with `/`:

```javascript
if (commandId.indexOf('nav.') === 0) {
  var url = row.getAttribute('data-url');
  closePalette();
  // Defense-in-depth: only allow same-origin path-absolute URLs. Rejects
  // javascript:, data:, mailto:, and any cross-origin redirect.
  if (url && url.charAt(0) === '/' && url.indexOf('//') !== 0) {
    window.location.href = url;
  }
  return;
}
```

Add a server-side invariant test (extend `CommandPaletteTests.Registry_NavRows_AllHaveAbsoluteAdminUrl`)
that asserts every `Url` matches `^/admin(/|$)` exactly so misconfigured `Url:` values
trip CI rather than ship.

### WARNING-GAP-02: `PlayerDetailPane.LoadAsync` uses `ConfigureAwait(false)` inside a Blazor component method that subsequently calls `StateHasChanged()` — anti-pattern documented in `microsoft/aspnetcore` Blazor guidance

**File:** `src/GameKit.Admin.UI/Components/Shared/PlayerDetailPane.razor:264-274, 296`

**Issue:**

```csharp
var banRow = await Db.AdminAuditLog.AsNoTracking()
    …
    .FirstOrDefaultAsync(ct).ConfigureAwait(false);          // ← ConfigureAwait(false)
…
_bannedByName = await PlayerNames.ResolveAsync(banRow.ActorId.Value, ct).ConfigureAwait(false);
…
// continues to LINQ join + ToListAsync (no ConfigureAwait) + StateHasChanged()
_loading = false;
StateHasChanged();
```

Blazor Server's renderer uses a custom `SynchronizationContext` (`RendererSynchronizationContext`)
to serialize re-renders against component state. `ConfigureAwait(false)` opts the
continuation off that context, and the subsequent `StateHasChanged()` call from a non-
renderer thread can throw `InvalidOperationException: The current thread is not associated
with the Dispatcher.` in some hosting configurations, or — more commonly in Blazor Server —
silently render on a thread-pool thread and race against any concurrent `OnParametersSetAsync`
re-entry. Microsoft's own Blazor guidance is "do not use `ConfigureAwait(false)` in
components." The two ConfigureAwait(false) calls were freshly added by Plan 03.1-11; the
pre-existing `Db.Players...FirstOrDefaultAsync` call on line 247 correctly omits it.

This is a regression introduced by the gap-closure plan; the rest of the file (and the
sibling `OpenBanDialog`/`OpenUnbanDialog`/`OpenGdprDialog` methods) intentionally do not
use `ConfigureAwait(false)` because the renderer requires the context.

**Fix:** Remove both `.ConfigureAwait(false)` calls (lines 270 + 273):

```csharp
var banRow = await Db.AdminAuditLog.AsNoTracking()
    .Where(r => r.Action == GameKit.Admin.UI.Services.AdminAuditActions.PlayerBan
                && r.TargetId == _player.Id)
    .OrderByDescending(r => r.CreatedAt)
    .ThenByDescending(r => r.Id)
    .Select(r => new { r.ActorId })
    .FirstOrDefaultAsync(ct);
if (banRow is not null && banRow.ActorId.HasValue)
{
    _bannedByName = await PlayerNames.ResolveAsync(banRow.ActorId.Value, ct);  // see BLOCKER-GAP-01 for the resolver swap
}
```

### WARNING-GAP-03: Three palette commands (`sign-out`, `rank-adjust`, `rotate-signing-key`) appear in the Cmd+K list but silently no-op on click — registry promises a verb the dispatcher does not implement

**Files:**
- `src/GameKit.Admin.UI/Services/AdminCommandRegistry.cs:39, 44, 46`
- `src/GameKit.Admin.UI/Components/Layout/MainLayout.razor:123-134`

**Issue:** `MainLayout.OpenDialog`'s switch only maps 5 of the 8 D-09 action verbs:

```csharp
var dialogType = commandId switch
{
    "ban"          => typeof(BanPlayerDialog),
    "unban"        => typeof(UnbanPlayerDialog),
    "gdpr-delete"  => typeof(GdprDeleteDialog),
    "create-admin" => typeof(CreateAdminDialog),
    "delete-admin" => typeof(DeleteAdminDialog),
    // rank-adjust + rotate-signing-key route to dialogs that may not yet exist in v1;
    // they are filtered out at the registry layer (Plan 04) for this release.
    _ => null
};
if (dialogType is null) return;
```

The comment claims the registry filters them out — but the registry **does not**:
`AdminCommandRegistry.AllCommands` includes `rank-adjust` (line 39), `rotate-signing-key`
(line 44), and `sign-out` (line 46). All three render in the palette (a superadmin sees
all three; a plain admin sees `sign-out`). Clicking any of them dispatches into
`MainLayout.OpenDialog`, falls through the switch, hits `_ => null`, and returns silently
— the palette closes, no dialog opens, no toast, no console error.

For `sign-out` in particular this is a UX trap: an operator hits Cmd+K → "Sign out" →
nothing happens → tries again → still nothing → assumes the menu is broken. The actual
sign-out path is the user-menu Logout item in `TopNav.razor:54`. The palette row should
either dispatch sign-out via the same `OnLogoutAsync` flow or be removed from the registry
until the dispatch path exists.

**Fix:** Two coupled changes:

1. **Registry-side** — remove `rank-adjust` + `rotate-signing-key` from `AllCommands`
   until their dialogs exist (the comment in `MainLayout.OpenDialog` says this was the
   intent), and add a unit-test invariant that asserts every non-`nav.*` registry id has
   a corresponding switch arm in `OpenDialog`. The invariant lives next to the existing
   `Registry_NavRows_AllHaveAbsoluteAdminUrl` test in `CommandPaletteTests`.

2. **Sign-out** — either give it a dedicated dispatch path (`commandId === 'sign-out'` →
   call `/admin/api/logout` from JS + redirect to `/admin/login`, mirroring
   `TopNav.OnLogoutAsync`), OR demote it to a `nav.sign-out` row with
   `Url: "/admin/login"` and let the user-menu Logout flow remain the canonical sign-out.

Document explicitly in the `AdminCommandRegistry` XML doc which verbs ship with dispatch
support in v1 vs. which are reserved for v2.

### WARNING-GAP-04: Stale `_renderTargetResults` overwrites the palette DOM after `closePalette()` — late fetch resolves into a hidden palette and corrupts state for the next open

**File:** `src/GameKit.Admin.UI/wwwroot/gamekit-admin.js:330-353, 102-115`

**Issue:** Sequence:

1. Operator opens palette, picks "Ban player" (`requiresTarget=true` → `_enterTargetPick`).
2. Operator types "alic" → `_onTargetSearchInput` fires → fetch dispatched with
   `_searchAbort.signal`.
3. Operator hits Esc → `closePalette()` runs, removes `data-palette-open` attribute,
   resets `_selectedAction = null`, removes the input listener — **does not** call
   `_searchAbort.abort()`.
4. Fetch resolves a few hundred ms later → `_renderTargetResults(rows)` mutates
   `.palette-list` → palette is hidden but its DOM is now in target-pick state with
   stale "Players" section + buttons.
5. Operator hits Cmd+K → `openPalette()` reveals the palette — but the rendered list is
   the stale target-pick subview, not the original action list.

The next palette filter (`_filterPalette` on user input) is keyed against `button.palette-row`
and sections, but the underlying server-rendered command list has been replaced wholesale.
The operator must reload the page to recover.

**Fix:** Abort any in-flight target search inside `closePalette`:

```javascript
function closePalette() {
  document.documentElement.removeAttribute('data-palette-open');
  if (_searchAbort) {
    try { _searchAbort.abort(); } catch (e) { /* noop */ }
    _searchAbort = null;
  }
  if (_selectedAction !== null) {
    _selectedAction = null;
    document.removeEventListener('input', _onTargetSearchInput);
    var input = document.querySelector('.palette-input input');
    if (input) {
      input.value = '';
      input.placeholder = 'Type a command…';
    }
  }
  if (_paletteOpener && _paletteOpener.focus) _paletteOpener.focus();
  _paletteOpener = null;
}
```

Also: when target-pick is cancelled mid-flight, the original SSR-rendered command list
DOM is gone (it was replaced by `_enterTargetPick` clearing `list.firstChild`). Even with
the abort fix, re-opening the palette after a cancelled target-pick will show an empty
list. The fix is to either snapshot+restore the original `.palette-list` innerHTML before
entering target-pick, OR force a full re-render path. Capture in the same fix.

### WARNING-GAP-05: `MatchHistoryRow` XML-doc `param` name `Delta` does not match the constructor parameter `RatingDelta` — XML-doc compliance check fails

**File:** `src/GameKit.Admin.UI/Http/AdminEndpoints.cs:551, 560`

**Issue:**

```csharp
/// <param name="RatingBefore">Rating snapshot at session start.</param>
/// <param name="RatingAfter">Rating snapshot at session end.</param>
/// <param name="Delta">Rating delta (RatingAfter - RatingBefore).</param>     ← param name "Delta"
/// <param name="CompletedAt">UTC timestamp of completion.</param>
public sealed record MatchHistoryRow(
    Guid SessionId,
    Guid? LadderId,
    int Team,
    string? Result,
    double? RatingBefore,
    double? RatingAfter,
    double? RatingDelta,                                                       ← parameter name "RatingDelta"
    DateTimeOffset? CompletedAt);
```

The parameter is named `RatingDelta` but the XML doc references `Delta` — the C# compiler
emits `CS1572: XML comment has a param tag for 'Delta', but there is no parameter by that
name`. CLAUDE.md mandates "XML doc comments on every public API — no exceptions"; this is
both a missing doc (for `RatingDelta`) and a stale doc (for the non-existent `Delta`). Was
not introduced by 03.1-10/11 but is on a record that ships in this phase's API surface, so
worth catching here.

**Fix:** Rename the param tag:

```csharp
/// <param name="RatingDelta">Rating delta (RatingAfter - RatingBefore).</param>
```

### INFO-GAP-02: `App.razor` `apiBase` computation does not handle empty `MountPath` value

**File:** `src/GameKit.Admin.UI/Components/App.razor:36-38`

```csharp
var apiBase = (AdminOptions.Value.MountPath ?? "/admin").TrimEnd('/') + "/api";
```

`GameKitAdminOptions.MountPath` is typed `PathString` (per the middleware constructor at
`AdminCspNonceMiddleware.cs:43`), which has an implicit-conversion to `string?`. If a host
app sets `MountPath = ""` (empty PathString — represents root mount), `?? "/admin"` does
**not** fire (empty PathString converts to non-null `""`), so `apiBase` becomes
`"" + "/api"` = `"/api"`. The JS bundle then fetches `/api/players/search` instead of the
intended path. This is unlikely (root mount of admin would conflict with the host app's
own routes) but the `?? "/admin"` defensive fallback is silently bypassed for a value the
fallback was clearly written to catch.

**Fix:** `IsNullOrEmpty`-guard the value:

```csharp
var mp = AdminOptions.Value.MountPath.Value;  // PathString.Value -> string
var apiBase = (string.IsNullOrEmpty(mp) ? "/admin" : mp.TrimEnd('/')) + "/api";
```

### INFO-GAP-03: `gamekit-admin.js` re-applies `applyAttrs(loadTweaks())` at script-load on top of the `App.razor` inline init — the `aria-checked` reflection iterates an empty NodeList because TweaksPanel may not yet be in the DOM

**File:** `src/GameKit.Admin.UI/wwwroot/gamekit-admin.js:422`

The bottom-of-file `applyAttrs(loadTweaks());` runs immediately when the deferred
`<script>` evaluates. Per the architecture comment, the FOUC eliminator in `App.razor`
already sets `[data-*]` attributes on `<html>` synchronously before paint; this re-apply
is "idempotent" for the html-element attributes, but the new aria-checked iteration in
`applyAttrs` (Plan 03.1-11 fix for WARNING-01) targets `button[data-tweak][data-value]`
nodes that live inside `TweaksPanel`. `TweaksPanel` is mounted inside `MainLayout`, which
attaches via the Blazor circuit AFTER the deferred script runs — so the initial reflection
finds zero buttons. The first user open of the panel won't show the active option until
the user clicks one (which fires `saveTweaks` → `applyAttrs` → reflection now finds the
buttons).

**Impact:** Cosmetic — opening Tweaks for the first time shows no active selection
indicator on any group; first interaction triggers correct reflection thereafter. UX
inconsistency vs. the sketch.

**Fix:** Re-run `applyAttrs(loadTweaks())` once when the panel opens. Hook it from
`openTweaks`:

```javascript
function openTweaks() {
  _tweaksOpener = document.activeElement;
  document.documentElement.setAttribute('data-tweaks-open', 'true');
  applyAttrs(loadTweaks());   // re-reflect aria-checked now that the panel is in the DOM
}
```
