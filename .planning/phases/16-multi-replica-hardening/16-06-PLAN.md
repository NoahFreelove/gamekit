<objective>
Prove multi-replica SignalR correctness (SCALE-06) for BOTH the Lobby and Admin hubs under replica restart and Redis reconnect.

- Lobby: two `LobbyTestApp` replicas share the real Testcontainers Redis backplane; a `LobbyHub` event broadcast from one replica reaches a client connected to the other replica even after Replica A is restarted, and events resume after a Redis reconnect.
- Admin: two `AdminTestHost` replicas share the same Redis. The Admin path is distinct from Lobby — `AdminEventHub` is receive-only, and cross-replica delivery flows through the `gamekit:admin:events` Redis Pub/Sub channel that each replica's `AdminLiveBroadcastService` subscribes to and relays to its locally-connected admin clients via `IHubContext<AdminEventHub>`. The Admin test publishes to `gamekit:admin:events`, restarts the publishing replica, and asserts an admin client on the OTHER replica still receives `ReceiveAdminEvent` (relay survives replica restart), plus a reconnect scenario.

Document the operator sticky-session requirement (the Redis backplane handles outbound fan-out, but hub method invocations must reach the same hub instance — affinity is an LB responsibility), covering both hubs.

Purpose: Demonstrate that Lobby AND Admin hub events fan out correctly across replicas under restart and reconnect — the multi-replica deploy invariant for real-time features (RESEARCH §SignalR Backplane + Open Question #4). Verifies SCALE-06 in full (Lobby + Admin).
Output: `SignalRReplicaTests` (Lobby) + `AdminSignalRReplicaTests` (Admin) + a short architecture doc with the sticky-session note.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Lobby client ↔ replica (WebSocket) ↔ Redis backplane | LobbyHub events must fan out across replicas; client invocations must reach a live hub instance |
| Admin client ↔ replica (WebSocket) ↔ gamekit:admin:events Pub/Sub relay | Admin events published on any replica must reach admin clients on every replica via AdminLiveBroadcastService; only cookie-authenticated admins may connect to AdminEventHub |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-06-01 | Tampering | SignalR channel-prefix collision across concurrent test runs | mitigate | Lobby test hosts use a per-test-run unique `ChannelPrefix` (`GameKit:{Guid:N}`); production prefix unchanged. Admin tests reuse the shared-Postgres `ResetAdminUsers` TRUNCATE guard + distinct seeded usernames per host (mirrors AdminEventHubTests) so concurrent admin-row seeds do not collide |
| T-16-06-02 | Denial of Service | Lost events on Redis reconnect mistaken for a correctness bug (both LobbyHub and the gamekit:admin:events relay) | accept | At-most-once during the outage window is documented (StackExchange.Redis auto-reconnect restores both the backplane subscription and the AdminLiveBroadcastService relay subscription); sticky sessions scope the loss — operator-documented, not a code defect |
| T-16-06-03 | Spoofing | AdminEventHub connection in the cross-replica admin test | accept | The Admin replica test authenticates the hub client with a real admin cookie (login → gk_admin_session → CookieInjectingHandler), exercising the production cookie-scheme gate; it does NOT bypass auth — the existing AdminEventHubTests SC#2(a)/(b) already prove unauthenticated/JWT rejection |
| T-16-06-SC | Tampering | npm/pip/cargo installs | accept | No new packages and no new test project — existing SignalR.StackExchangeRedis shared framework + xUnit/Testcontainers + the already-present GameKit.Admin.Integration.Tests + GameKit.Lobby.Integration.Tests projects |
</threat_model>
