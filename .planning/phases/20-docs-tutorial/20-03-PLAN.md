<objective>
Deliver the getting-started tutorial (DOCS-02) and, critically, the CI smoke test that proves the tutorial happy-path actually works end-to-end. This is the highest-risk deliverable in the phase.

The smoke test boots an in-process host with the full GameKit chain against Testcontainers Postgres + Redis, then drives the exact tutorial path: two guest logins → enqueue two tickets with `poolName: null` → poll status until the in-process ticker advances a ticket to the `proposed` state and exposes a non-null `ProposalId` → both players accept using that `ProposalId` (the second accept confirms the all-accepted / match-formed outcome) → assert `GET /health/ready` returns 200.

**Architecture decision — RESEARCH Open Question 2 is RESOLVED: hand-rolled in-process host, NOT `WebApplicationFactory<Program>`.** The established pattern in `tests/GameKit.OpenApi.Integration.Tests/OpenApiTestApp.cs` deliberately hand-builds an in-test host that mirrors `samples/TicTacToeDuel/Program.cs` rather than using `WebApplicationFactory<Program>`, because the sample's Program is internal-by-default and standing up the real sample needs on-disk JWT keys + appsettings. Mirror that proven pattern (ephemeral RSA keypair, per-test fresh database, full Add*+Map* chain, in-process matchmaking ticker). This is more robust than WebApplicationFactory against the sample and matches how every other GameKit integration test boots. The `public partial class Program` that Plan 20-01 adds to the sample is NOT consumed here (it is a forward-looking affordance for future WAF-based tests); this plan does not reference the sample's Program type at all.

Three deliverables make the gate honest:
1. **Host actually boots** — a dedicated boot [Fact] constructs + initializes `TutorialSmokeTestApp` (with its in-process matchmaking ticker) and asserts it is up, so Task 2 is built on a proven-live host rather than a merely-compiling type.
2. **Match genuinely forms** — the happy-path test extracts the non-null `ProposalId` from the `proposed`-status response and drives it through BOTH accept calls; it fails fast (≤10s, never hangs) if no proposal forms.
3. **CI runs it** — `.github/workflows/ci.yml` gains a dedicated step running the smoke test on push to main.

Purpose: An honest, reproducible-offline CI gate that the documented tutorial path forms a match and the app reaches readiness.
Output: A new `tests/GameKit.Tutorial.SmokeTests/` project (added to the solution), a CI step in `.github/workflows/ci.yml`, and `docs/tutorial/getting-started.md`.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-03-01 | Information disclosure | tutorial localStorage JWT guidance | mitigate | The tutorial echoes the existing in-page demo-only XSS callout; it does not present localStorage as production-safe. |
