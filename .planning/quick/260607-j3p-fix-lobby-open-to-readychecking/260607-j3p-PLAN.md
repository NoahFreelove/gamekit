<objective>
Fix a live-exercise v2.0 Lobby bug: a lobby created through the public API (`POST /api/lobbies`)
is stuck in `LobbyState.Open` forever and can never reach `ReadyChecking`/`InGame`. The headline
LOBBY-03 ready-check → matchmaking flow is therefore unreachable in real usage — it only ever
worked in tests because `LobbyTestApp.SeedLobbyAsync` inserts `State=1 (ReadyChecking)` directly
via raw Npgsql, masking the missing `Open→ReadyChecking` edge.

Root cause (already diagnosed — do NOT re-investigate): `LobbyService` only ever assigns `State` =
`Open` (CreateLobbyAsync), `InGame` (MarkReadyAsync all-ready gate, which is itself GATED on
`State == ReadyChecking`), and `ReadyChecking` (RevertToReadyCheckingAsync, reachable only FROM
InGame). There is no `Open→ReadyChecking` edge, so the MarkReady all-ready gate never fires.

User-approved fix: "auto-start when full" — when a join fills the lobby to `MaxMembers` and the
lobby is still `Open`, transition it to `ReadyChecking` and broadcast. Do NOT add a new
endpoint/hub method; do NOT auto-transition on create.

Secondary fix: member-count over-count. Both `JoinLobbyAsync` and `CreateLobbyAsync` call
`lobby.Members.Add(member)` AFTER `_ctx.Set<LobbyMemberEntity>().Add(member)`. EF relationship
fixup already adds the tracked member to `lobby.Members`, so the explicit Add duplicates the
reference and `lobby.Members.Count` over-reports (live: REST join returned memberCount=3 for a
2-member lobby).

Purpose: make the documented LOBBY-03 flow actually reachable through the public API and stop
the cosmetic member over-count.
Output: runtime-behavior fix in LobbyService (no migration, no new public API), one new
integration test file proving the full lifecycle FROM Open, and a RESOLVED tech_debt note.
</objective>
