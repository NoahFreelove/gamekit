# Project Research Summary

**Project:** GameKit v2.1 — Operability & Hardening
**Domain:** Self-hosted GPL .NET 10 game-services library — production hardening (no new game-services surface)
**Researched:** 2026-06-08
**Confidence:** HIGH (all NuGet versions verified on nuget.org; all architecture claims grounded in live codebase inspection; all license facts sourced from official repos/pages)

---

## Executive Summary

GameKit v2.1 is a hardening milestone on top of a mature, shipped v2.0 codebase. It adds no new game-services features. The goal is to make existing packages production-observable, K8s/Docker-probe-ready, multi-replica-proven, backup-recoverable, security-audited, load-tested, and fully documented. Because the library is GPL, self-hosted, and zero-cloud, every operability addition must be either entirely opt-in (OTel SDK, Prometheus scraping) or architecture-neutral (health endpoints that work without Admin.UI, CLI DR tooling that runs as a separate process, load tests that never require SaaS). The hard invariants that constrain every v2.1 decision: opt-in everything; GPL-compatible licenses only; no SaaS dependencies in any code path; no PII or secrets in any observable output; zero phone-home.

The research resolves all major stack picks cleanly. The OTel SDK (1.15.3 GA, Apache-2.0) promotes from the existing v2.0 API-only seam to a full SDK+OTLP exporter as an opt-in hard dependency in `GameKit.Core`; EF Core and Redis instrumentation packages remain beta and are confined to the sample app. Health endpoints go into `GameKit.Core` via `MapGameKitHealth()` — a new `GameKit.Diagnostics` package is explicitly rejected. Load testing uses k6 (AGPLv3 CLI, not a library dep) plus BenchmarkDotNet (MIT), with NBomber excluded because its v5 license bars organizational use. Docs are generated by DocFX 2.78.5 (MIT, net10.0), with Statiq excluded due to a commercial restriction incompatible with GPL. CVE scanning uses the .NET SDK's built-in NuGetAudit (NuGetAuditMode=all, the .NET 10 default) plus Trivy for container-level coverage.

The principal risk this milestone must tame is the intersection of multi-replica correctness and observability: split-brain from `LockTtlSeconds=90` against the 50ms ticker budget under real Redis RTT, and PII leaking into OTel spans (a GDPR violation AND a GPL self-hosted breach if spans flow to a SaaS exporter). Both risks must be addressed before Phase 19 load tests run against the final codebase. One architectural tension remains unresolved and is flagged as an open question for the requirements step: whether a thin `GameKit.Observability` convenience-wrapper package should exist (FEATURES.md recommendation) or whether a Core extension method is sufficient (ARCHITECTURE.md preference).

### Architecture Approach

The central architecture decision for v2.1 is **extending `GameKit.Core` rather than creating a new `GameKit.Diagnostics` package.** Health endpoints and OTel builder extensions go into Core because: (a) they are operational necessities any consumer needs, not optional features; (b) the OTel `ActivitySource`/`Meter` seam already lives in Core; (c) adding a package grows the release train and adds a required pin consumers cannot skip; (d) `GameKitDbContext` and the connection string already live in Core, making the Postgres probe a natural co-location. Admin.UI's `HealthProbeService` is refactored to delegate its Postgres + Redis probes to the new Core-level `CoreHealthProbe`; the Admin-specific error-rate ring buffer stays in Admin. Dependency direction remains clean: Core does not depend on Admin.UI.

**Major new components:**

| Component | Package | Purpose |
|-----------|---------|---------|
| `GameKitTelemetry` static class | `GameKit.Core` | Naming-convention string constants (`GameKit.*` source prefix, attribute keys) — prevents per-package drift |
| `ILeaderLease` interface | `GameKit.Core` | Common contract for all three existing `LeaseHelper` classes; single auditable implementation |
| `IMigrationReadinessReporter` interface | `GameKit.Core` | Per-package migration state; readiness endpoint resolves `IEnumerable<IMigrationReadinessReporter>` → 503 until all ready |
| `AddGameKitObservability()` builder extension | `GameKit.Core` | Opt-in OTel SDK wiring; consumer decides exporters |
| `MapGameKitHealth()` endpoint extension | `GameKit.Core` | `/health/live` + `/health/ready`; available without `GameKit.Admin.UI` |
| `CoreHealthProbe` | `GameKit.Core` | Postgres `SELECT 1` via pool connection (not new `DbContext`) + optional Redis `PingAsync()` |
| Per-package `Telemetry/` classes | Auth, Rankings, Presence, Lobby, Admin.UI | `ActivitySource`/`Meter` per package following the Matchmaking pattern already in the codebase |
| `docker-compose.observability.yml` | `samples/TicTacToeDuel` | Grafana + Prometheus + Tempo overlay; internal Docker network isolates `/metrics` |
| `tests/GameKit.LoadTests/` | `tests/` | BenchmarkDotNet micro-benchmarks + k6/Testcontainers end-to-end load harness; not shipped |
| `docs/` + `docfx.json` | repo root | DocFX site config; build artifact, not shipped |

**Key data-flow decisions:**
- W3C trace context serialized into the Redis ticket hash at enqueue time; restored in the ticker via `Activity.SetParentId()` — the only correct way to propagate trace context across a `PeriodicTimer` background service boundary
- `ReleaseLeaseAsync` MUST use `CancellationToken.None` on SIGTERM drain paths — `stoppingToken` would cause the lock to remain held until the 90-second TTL expires
- Liveness probe is always-200; `IHealthProbeService.ProbeAsync` (Postgres + Redis) belongs to readiness and the admin panel, not liveness
- Redis health check is tagged `"redis"` and informational only; Redis failure does NOT flip a pod unready — Polly handles transient Redis failures at the application level

**Suggested build order:** Phase 13 → 14 → 15 → 16 → 17 → 18 → 19 → 20 (see Implications section)

### Critical Pitfalls — Watch Out For

The full pitfall list (12 pitfalls) is in `.planning/research/PITFALLS.md`. The three highest severity:

**1. PII / secrets in OTel spans (GPL + GDPR landmine) — Phase 13, first task**
A `SetTag` call with `playerId`, `username`, or an auth exception message is a GDPR data leak and — if spans flow to a SaaS OTLP endpoint — a GPL self-hosted breach. Risk points: match-formation child spans, Auth login exception attributes, Lobby SignalR message body tags. Prevention: establish a **span attribute allow-list** (structural IDs only: ladder ID, session ID, pool name; never player-identifying data) and add a CI lint gate (`grep -r 'SetTag.*playerId\|SetTag.*username'`) before any per-package instrumentation is written. This lint gate is the first task of Phase 13 — not the last.

**2. Split-brain from `LockTtlSeconds=90` vs. 50ms ticker budget under realistic Redis RTT — Phase 16 gate**
`GameKitMatchmakingTickerOptions.LockTtlSeconds=90`, `MaxIterationBudgetMs=50` (both confirmed in codebase). Under load with real network Redis RTT (2–5ms/op × ~32 ops/tick = 160ms >> 50ms budget), the ticker overshoots, misses renewal windows, and the lock expires mid-sweep. Replica B acquires the lock. If Replica A's pool-sweep loop continues after `RenewLeaseAsync` returns `false`, both replicas form matches simultaneously — duplicate `game_sessions` rows. Prevention: the renewal check must be the first operation inside each pool-sweep loop body, not just at the top of the tick; bail the entire tick immediately on `false`. Add `MatchmakerSplitBrainTests` (two-replica Testcontainers + simulated lease expiry) as a CI gate before Phase 19 load tests run.

**3. Unauthenticated Prometheus `/metrics` endpoint — Phase 13 gate**
`UseOpenTelemetryPrometheusScrapingEndpoint()` maps `/metrics` with no auth, exposing queue depths per ladder, error rates, and internal counters. Prevention: GameKit must never auto-register this endpoint; the sample `docker-compose.observability.yml` must isolate it on a `gamekit-internal` Docker network (not a published host port); the tutorial must show auth-gated metrics from the first code example. Add a startup `LogWarning` when `ASPNETCORE_ENVIRONMENT=Production` and the Prometheus endpoint is registered without authorization.

- **Phase 13 before Phase 15:** Naming conventions before per-package instrumentation prevents immediately needing to rename instruments. PII lint gate before any `SetTag` calls are written.

- **Phase 16 after Phase 14–15:** Multi-replica hardening benefits from both health-probe visibility (readiness transitions) and OTel trace visibility (leader-election spans in Tempo).
- **Phase 17 in parallel with 15–16 if staffed:** No dependency on telemetry or hardening; CLI subcommands and runbooks are independent work streams.
- **Phase 18 after Phases 13–17:** Security audit of completed code. CVE gate is Phase 18's first task.
- **Phase 19 after Phase 18:** Load tests run against the final audited codebase. `MatchmakerSplitBrainTests` from Phase 16 is a prerequisite gate.
- **Phase 20 last:** API surface stable; tutorial targets the fully-integrated sample app.

## Open Questions

### Unresolved Scope Tension: `GameKit.Observability` Convenience Package vs. Core Extension Method

**FEATURES.md recommends:** A thin `GameKit.Observability` NuGet package that wires all `ActivitySource`s, `Meter`s, and an OTLP exporter in a single call. Reduces consumer boilerplate from ~20 lines to 1; zero runtime behavior; still strictly opt-in.

**ARCHITECTURE.md recommends:** Extend `GameKit.Core` with an `AddGameKitObservability()` builder extension. Avoids adding a 10th package to the release train; observability is an operational necessity (not optional feature); all OTel seams already exist in Core.

**Practical difference:** Whether `OpenTelemetry` 1.15.3 (~1.5 MB) appears as a transitive dep for every `GameKit.Core` consumer or only for consumers who explicitly install `GameKit.Observability`. With opt-in activation (consumer must call `AddGameKitObservability()`), the OTel packages are soft transitive deps either way — they are dead weight unless activated.

**For the requirements step:** Decide before Phase 13 planning begins. If `GameKit.Observability` is chosen, add it to `Directory.Build.props` and version-bump automation. If Core extension is chosen, `OpenTelemetry` 1.15.3 + siblings become hard deps of `GameKit.Core`. One sentence in REQUIREMENTS.md closes this question.
