# Upgrade guide: v2.0 → v2.1

This guide covers every consumer-facing change you must make when upgrading a
v2.0 GameKit application to v2.1. Every extension method, configuration key, and
migration timestamp listed here was verified against the shipped source.

> **Tested upgrade path:** The [getting-started tutorial](../tutorial/getting-started.md)
> and the TicTacToeDuel sample app boot under v2.1 with these changes applied.

---

## Summary of changes

| Area | Change | Consumer action |
|------|--------|-----------------|
| Observability | `AddGameKitObservability()` | **Required** — call after all `AddXxx` extensions |
| Health checks | `AddGameKitHealthChecks()` + `MapGameKitHealth()` | **Required** — register + map |
| Leader-lease abstraction | `ILeaderLease` internal consolidation | Usually none — see note |
| MessagePack security pin | MessagePack 3.1.7 eliminates GHSA-hv8m-jj95-wg3x | Remove old workaround if present |
| Migration ordering markers | DrOrdering marker migrations per-package | None — auto-apply on startup |
| NuGet audit policy | `NuGetAuditMode=all` + `NuGetAuditLevel=high` | Ensure `Directory.Build.props` is current for source builds |

---

## 1. AddGameKitObservability (Phase 13/15 — OBS-01/04/05/06)

GameKit v2.1 ships an opt-in OpenTelemetry integration. Call
`AddGameKitObservability()` **after all other `AddXxx` extension calls** and
before `builder.Build()`.

```csharp
// After gameKitBuilder.AddLobby(), .AddAuth(), .AddMatchmaking(), etc.
gameKitBuilder.AddGameKitObservability(otel =>
{
    // Set to your OTLP endpoint (e.g. "http://localhost:4317" for the sample
    // OTel Collector). Leave null if you are not running an observability stack —
    // GameKit will still register its ActivitySources and Meters so any OTel SDK
    // already in your host can discover them.
    otel.OtlpEndpoint = builder.Configuration["GameKit:Observability:OtlpEndpoint"];
});
```

If you also want HTTP server-span instrumentation (so that GameKit child spans
appear nested under the inbound request span), opt in at the host level:

```csharp
// This is a host decision — GameKit does not force ASP.NET Core instrumentation
// on consumers (air-gap guarantee: no telemetry leaves your network unless you
// configure an OTLP endpoint).
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing.AddAspNetCoreInstrumentation());
```

**The `OtlpEndpoint` key is consumer-configured.** GameKit never hard-codes an
endpoint and never sends telemetry to any external service. See
[ADR-0009](../adr/0009-otel-opt-in.md) for the design rationale.

**Appsettings example:**

```json
{
  "GameKit": {
    "Observability": {
      "OtlpEndpoint": "http://localhost:4317"
    }
  }
}
```

Leave the key absent (or set to `null`) in environments without an observability
stack. `AddGameKitObservability` is still required — omitting it means no
`ActivitySource` or `Meter` is registered.

## 2. AddGameKitHealthChecks + MapGameKitHealth (Phase 14 — HLTH-01/02)

v2.1 ships a health-check subsystem. Registration must come **after all `Add*`
extension calls** so that the `IConnectionMultiplexer` (Redis) is already in DI
when the Redis readiness probe is wired. Mapping is done in the endpoint section.

```csharp
// REGISTRATION — after gameKitBuilder.AddMatchmaking(), .AddPresence(), etc.
gameKitBuilder.AddGameKitHealthChecks();

var app = builder.Build();

// MAPPING — in the endpoint section (before or after MapGameKit/MapAuth)
app.MapGameKitHealth();   // exposes GET /health/live  (liveness)
                          //          GET /health/ready (readiness — Postgres + Redis + migrations)
```

**Exposed endpoints:**

| Endpoint | Probe type | Returns |
|----------|------------|---------|
| `GET /health/live` | Liveness | `200 Healthy` always (process is up) |
| `GET /health/ready` | Readiness | `200 Healthy` / `503 Unhealthy` based on Postgres, Redis, and pending migrations |

The readiness response body lists each named health-check component:

```json
{
  "status": "Healthy",
  "entries": {
    "postgres": { "status": "Healthy" },
    "redis": { "status": "Healthy" },
    "migrations": { "status": "Healthy" },
    "matchmaking_leader_lock": { "status": "Healthy" }
  }
}
```

Use `GET /health/ready` in your load-balancer health check and Kubernetes
readiness probe. Use `GET /health/live` in your Kubernetes liveness probe.

See also the [matchmaking outage runbook](../runbooks/matchmaking-outage.md) for
how to interpret the `matchmaking_leader_lock` component during an incident.

## 3. ILeaderLease — internal consolidation (Phase 16 — SCALE-01)

`ILeaderLease` is a new internal abstraction that consolidates the per-background-
service lease helpers (`MatchmakerLeaseHelper`, `RankDecayLeaseHelper`,
`RankingsTickerLeaseHelper`) behind a single, testable interface.

**Consumer action: usually none.** If you use the standard `AddMatchmaking()` /
`AddRankings()` builder pattern you are unaffected — the consolidation is internal.

**Affected only if you injected the concrete helpers by type.** If your code has:

```csharp
// Only affected if you resolved these concrete types directly:
services.GetRequiredService<MatchmakerLeaseHelper>();
services.GetRequiredService<RankDecayLeaseHelper>();
services.GetRequiredService<RankingsTickerLeaseHelper>();
```

Replace with constructor injection via `ILeaderLease` from the
`GameKit.Core.Leader` namespace. The concrete helpers are no longer registered
in DI — only the `ILeaderLease` interface is.

**SIGTERM / drain semantics (SCALE-05):** When the host receives `SIGTERM` the
active leader-tick iteration runs to completion and then the lease is released
with `CancellationToken.None` (ensuring release even after the host's cancellation
token is already cancelled). See the
[rolling-deploy runbook](../runbooks/rolling-deploy.md) for the operator
implications.

## 4. MessagePack 3.1.7 transitive pin (Phase 18 — SEC-07)

v2.1 adds a transitive pin to `Directory.Packages.props` to eliminate the
high-severity CVE GHSA-hv8m-jj95-wg3x in the MessagePack versions previously
pulled in transitively by `GameKit.Lobby` (via SignalR's MessagePack protocol
support).

```xml
<!-- Directory.Packages.props — present in the shipped source -->
<PackageVersion Include="MessagePack" Version="3.1.7" />
<PackageVersion Include="MessagePack.Annotations" Version="3.1.7" />
```

**If you previously added `-p:NuGetAudit=false` as a workaround for the
`NU1903` MessagePack advisory: remove it.** The advisory is fixed by the pin,
not suppressed. Continuing to pass `-p:NuGetAudit=false` defeats the audit for
all packages, not just MessagePack.

Consumers who build GameKit from source and use Central Package Management
(`ManagePackageVersionsCentrally=true`) inherit the pin from
`Directory.Packages.props` automatically.

## 5. DrOrdering marker migrations (Phase 17 — DR-07)

Each package gained a no-op "ordering marker" migration in v2.1. These migrations
exist to establish a deterministic ordering point across packages after the
Phase 17 disaster-recovery work. They apply automatically during startup
(GameKit's `AutoMigrate` hosted service runs them in dependency order) and
**require no consumer action** beyond allowing migrations to run.

**Migration timestamps (for reference):**

| Package | Migration name | Timestamp |
|---------|----------------|-----------|
| `GameKit.Auth` | `DrOrderingMarker` | `20260623000000` |
| `GameKit.Core` | bundled into `AddGameSessionIdempotencyKey` | `20260622000000` |
| `GameKit.Admin.UI` | `DrOrderingMarker` | `20260624000000` |
| `GameKit.Rankings` | `DrOrderingMarker` | `20260625000000` |
| `GameKit.Matchmaking` | `DrOrderingMarker` | `20260626000000` |
| `GameKit.Lobby` | `DrOrderingMarker` | `20260627000000` |

> **Multi-replica note:** In multi-replica deployments the recommended practice
> is to run migrations as a separate pre-deploy step (`dotnet ef database update`
> with the owner connection string) before rolling out the new image. Do NOT run
> with `AutoMigrate=true` across multiple replicas simultaneously — the advisory
> lock per package prevents corruption but a racing `AutoMigrate` will block and
> slow your startup. See [docs/ops/migrations-runbook.md](../ops/migrations-runbook.md)
> and the [rolling-deploy runbook](../runbooks/rolling-deploy.md).

## 6. NuGetAuditMode = all (Phase 18 — SEC-07)

v2.1 sets the following in `Directory.Build.props` for all source builds:

```xml
<NuGetAuditMode>all</NuGetAuditMode>
<NuGetAuditLevel>high</NuGetAuditLevel>
```

**`NuGetAuditMode=all` audits both direct and transitive dependencies** (the
default `direct` only checks direct references). Consumers who build GameKit from
source inherit this policy automatically.

If a build warns about a different transitive advisory: consult
[docs/security-checklist.md](../security-checklist.md) for the CVE-pin pattern
(add a `<PackageVersion>` override in `Directory.Packages.props`, verify the
pinned version clears the advisory, document the reason in a comment).

## Wiring order (complete v2.1 example)

The following excerpt shows the v2.1 wiring order for all new extensions:

```csharp
var gameKitBuilder = builder.Services.AddGameKit(opts => { /* ... */ });

gameKitBuilder.AddAuth(/* ... */);
gameKitBuilder.AddRankings();
gameKitBuilder.AddMatchmaking();
gameKitBuilder.AddPresence();
gameKitBuilder.AddLobby();

// v2.1 additions — order matters:
gameKitBuilder.AddGameKitObservability(otel =>
{
    otel.OtlpEndpoint = builder.Configuration["GameKit:Observability:OtlpEndpoint"];
});

// Optional host-level HTTP instrumentation (consumer decision)
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing.AddAspNetCoreInstrumentation());

gameKitBuilder.AddGameKitHealthChecks();  // LAST — after all Add* that consume IConnectionMultiplexer

var app = builder.Build();

// ... middleware: UseRouting, UseRateLimiter, UseGameKitAuth, UseGameKit, ...

app.MapGameKitHealth();   // /health/live + /health/ready
app.MapGameKit();
app.MapAuth();
// ... other Map* calls
```

> **Full example:** `samples/TicTacToeDuel/Program.cs` — the reference
> application showing all wiring in production order.

## Verification

After applying these changes:

1. `GET /health/ready` → `200 Healthy` with all components listed.
2. `GET /health/live` → `200 Healthy`.
3. If you configured `OtlpEndpoint`: traces appear in your collector within the
   first player action (login, enqueue, match).
4. `dotnet build` produces zero `NU1903` warnings (MessagePack advisory cleared).
5. Migrations apply cleanly on first startup (check logs for
   `Applied migration: 20260623000000_DrOrderingMarker` per package).
